# حالة دمج TweetSMS الفعلي

## النطاق المعتمد

يدعم PowerHub حساب TweetSMS مركزياً لمنصة PowerHub، بينما تبقى حصة الرسائل وحدودها محصورة بكل صاحب مولد. لا تعرض واجهات المالكين أو سجل التدقيق مفاتيح الاعتماد، ولا يتغير وضع أي رسالة إلى **مسلّمة** ما لم يقدم المزود تقرير تسليم موثقاً.

| العنصر | الحالة الحالية | الضابط الأمني |
|---|---|---|
| عقد API-KEY ومسار الإرسال | موثق | تستقبل المنصة `999` للنجاح وتتعامل مع رموز الرفض المعروفة. |
| مفتاح API والرمز الإضافي | موجودان في أسرار بيئة المشروع | لا يخزنان في PostgreSQL ولا يظهران في الواجهة أو السجل. |
| فحص اتصال الحساب | ناجح في فحص حي محدود | استخدم `chk_user` فقط؛ لم يرسل رسالة ولم يقرأ بيانات مشتركين. |
| إعداد حساب المنصة | جاهز في الشفرة وSupabase | لا يصبح نشطاً تلقائياً عند تغيير الرابط أو اسم المرسل. |
| الإرسال الفعلي | غير مفعل حتى الآن | يتطلب نشر الدفعة، وحفظ إعداد الحساب، وفحص حساب/مرسل/رصيد، ثم موافقة صريحة على أول إرسال. |

## دورة التفعيل المقيدة

بعد نشر الدفعة على Vercel، تُدخل قيمتا `TWEETSMS_API_KEY` و`TWEETSMS_API_TOKEN` في أسرار **Production** من دون مشاركتهما في المحادثة. يحفظ مشرف المنصة رابط TweetSMS الرسمي واسم المرسل فقط في مركز الإدارة، ثم ينفذ فحصاً لا يرسل رسالة: يتحقق الفحص من الحساب واسم المرسل والرصيد إن كان الرمز الإضافي مطلوباً.

يظل الحساب غير نشط إذا تغيّر الرابط أو اسم المرسل أو فشل الفحص. بعد النجاح، يفعّل مشرف المنصة الحساب صراحة. يقتصر أول اختبار إرسال لاحق على رقم اختبار يحدده المستخدم وبنص غير تشغيلي، ولا يستخدم أي مشترك حقيقي أو فاتورة أو مزامنة.

## ملاحظات التوافق

يعتمد عميل TweetSMS مسار API-KEY الموثق `https://tweetsms.ps/api.php/maan/` وصيغة نموذج مرمز. لا تستخدم المنصة حقول المجموعات أو الجدولة في هذا الإطلاق، ولا تستعمل أي مفاتيح أو رموز ظاهرة في أمثلة الوثائق العامة. [1] [2]
