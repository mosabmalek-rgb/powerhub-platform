# دورة التطوير باستخدام شات جي بي تي

**المرجع التشغيلي لتطوير PowerHub وإضافة الميزات والتعديلات**

> هذه الوثيقة هي المرجع الأساسي الذي يجب على ChatGPT قراءته والالتزام به قبل تنفيذ أي تطوير جديد في المستودع.

## 1. الهدف

توحيد طريقة تطوير PowerHub ومنع الأخطاء الناتجة عن:

- التعديل المباشر على `main`.
- خلط أكثر من ميزة في فرع واحد.
- تنفيذ تغييرات غير موثقة في قاعدة البيانات أو Production.
- تجاوز الاختبارات أو إخفاء الأخطاء بدل إصلاحها.
- دمج عمل غير مكتمل أو غير متحقق منه.
- فقدان السياق بين جلسات التطوير المختلفة.

## 2. القاعدة الذهبية

`main` هو الخط المرجعي الوحيد المعتمد.

لا يتم التطوير مباشرة على `main`.

كل تغيير جديد يجب أن يمر عبر:

`main → Feature Branch → Implementation → Tests → PR → Review → Verification → Merge → Production Verification`

ولا يجوز اعتبار الميزة مكتملة لمجرد أنها تعمل محليًا.

## 3. مراحل دورة التطوير

### المرحلة 0 — تثبيت خط الأساس

قبل بدء أي عمل:

1. التحقق من أن `main` هو أحدث خط مرجعي.
2. التحقق من عدم وجود عمل غير معروف أو غير مرتبط بالميزة.
3. معرفة حالة Production الحالية.
4. عدم استخدام فرع قديم كمصدر لميزة جديدة إلا بعد فحصه صراحة.

**المخرج:** نقطة بداية معروفة ومستقرة.

### المرحلة 1 — تعريف الطلب

يتم تحديد:

- المشكلة أو الحاجة.
- الهدف.
- المستخدمون المتأثرون.
- السلوك المطلوب.
- ما يدخل ضمن النطاق.
- ما هو خارج النطاق.
- معايير القبول.

**المخرج:** Feature Specification واضحة.

### المرحلة 2 — تحليل النظام الحالي

قبل كتابة الكود، يجب فحص الأجزاء المتأثرة، بما في ذلك عند الحاجة:

- بنية المشروع.
- الصفحات والمكونات الحالية.
- الخدمات والواجهات.
- Supabase وقاعدة البيانات.
- RLS والسياسات.
- RPCs وEdge Functions.
- Authentication والصلاحيات.
- التكاملات الخارجية.
- الاختبارات الموجودة.
- الميزات المشابهة أو القديمة.

يجب عدم إعادة بناء وظيفة موجودة دون سبب واضح.

**المخرج:** Technical Impact Assessment.

### المرحلة 3 — التصميم المعماري

يتم تحديد التصميم قبل التنفيذ، ويشمل حسب الحاجة:

- Database schema.
- Tables / columns / relations.
- RLS policies.
- RPCs أو طبقة الخدمة.
- API أو Server Actions.
- Types.
- State management.
- Realtime / queues / notifications.
- Logging وAudit.
- Error handling.
- Security boundaries.
- Performance considerations.
- Backward compatibility.

**المخرج:** Technical Design.

### المرحلة 4 — خطة التنفيذ

تقسيم الميزة إلى مهام صغيرة وقابلة للتحقق.

النمط المفضل:

1. Database / Migration.
2. Security / RLS.
3. Backend / Services / RPC.
4. Types.
5. Frontend.
6. Integration / Realtime.
7. Tests.
8. E2E عند الحاجة.
9. Documentation.

**المخرج:** Implementation Plan.

### المرحلة 5 — إنشاء فرع مستقل

يتم إنشاء فرع جديد انطلاقًا من `main` الحالي.

مثال:

```text
main
  ↓
feature/admin-generator-chat
```

قواعد الفرع:

- ميزة واحدة أو نطاق مترابط واحد.
- لا تغييرات جانبية غير ضرورية.
- لا دمج لعمل قديم غير مفهوم.
- لا force-push على فرع مشترك دون سبب مضبوط.

**المخرج:** Feature Branch نظيف.

### المرحلة 6 — التنفيذ

تنفيذ الخطة تدريجيًا مع الحفاظ على حدود الميزة.

قواعد إلزامية:

- لا تعديل مباشر على Production أثناء التطوير.
- لا تعطيل اختبار لإخفاء فشل.
- لا إضافة workaround غير موثق.
- لا حذف كود مستخدم دون تحليل المراجع والاعتماديات.
- لا خلط ميزات مستقلة في نفس PR.
- أي تغيير في البيانات أو الصلاحيات يجب أن يكون مقصودًا وموثقًا.

### المرحلة 7 — الاختبارات المحلية

قبل فتح PR يجب تشغيل الاختبارات المناسبة، ومنها حسب طبيعة التغيير:

```text
TypeScript / Typecheck
Unit Tests
Integration Tests
Build
Lint
Static / Security Guards
Migration Validation
```

ويجب إصلاح الفشل الحقيقي بدل الالتفاف عليه.

**المخرج:** Local Green.

### المرحلة 8 — إنشاء Pull Request

يفتح PR من Feature Branch إلى `main`.

يجب أن يتضمن وصف PR:

- الهدف.
- المشكلة التي يحلها.
- ما تم تنفيذه.
- الملفات أو الأنظمة الحساسة.
- تغييرات قاعدة البيانات.
- التغييرات الأمنية والصلاحيات.
- الاختبارات المنفذة.
- المخاطر المعروفة.
- خطوات التحقق.

لا يستخدم PR واحد لعدة أعمال غير مترابطة.

### المرحلة 9 — CI / Automated Verification

يجب أن تمر التغييرات عبر فحوص CI المناسبة.

المبدأ:

```text
TypeScript
↓
Tests
↓
Build
↓
Security / Runtime Guards
↓
E2E عند الحاجة
```

**الفشل يعني التوقف والتحقيق.**

لا يتم تجاوز الفشل بتحويل الفحص إلى `skipped` أو إزالة الاختبار أو تغيير CI فقط للحصول على نتيجة خضراء.

### المرحلة 10 — المراجعة التقنية

يتم فحص التغيير كـ Code Review مستقل، مع التركيز على:

- Correctness.
- Security.
- Tenant isolation.
- RLS.
- Authentication / Authorization.
- Performance.
- Maintainability.
- Error handling.
- Edge cases.
- Backward compatibility.
- عدم كسر وظائف حالية.

في PowerHub تحديدًا يجب التحقق من عدم إمكانية وصول Tenant إلى بيانات Tenant آخر.

### المرحلة 11 — Preview / Staging Verification

قبل Production، يتم التحقق من السلوك الفعلي عبر Preview أو البيئة المناسبة.

حسب نوع الميزة يتم فحص:

- Login.
- Permissions.
- Happy path.
- Invalid input.
- Empty states.
- Mobile / Desktop.
- Network failure.
- Realtime.
- Error messages.
- أهم رحلة مستخدم متأثرة.

لا تعتبر اختبارات الوحدة وحدها كافية للميزات ذات الواجهات أو التكاملات.

### المرحلة 12 — مراجعة Production Database

إذا تضمنت الميزة Migration أو تغييرات على Production Database يجب تحديد مسبقًا:

- ما الذي سيتغير؟
- هل التغيير Backward Compatible؟
- هل توجد Data Migration؟
- هل توجد مخاطر فقد بيانات؟
- ما خطة الاسترجاع أو التراجع المناسبة؟
- هل تم اختباره قبل Production؟

لا ينفذ SQL عشوائي على Production.

### المرحلة 13 — الدمج إلى `main`

لا يتم الدمج إلا بعد اكتمال المتطلبات السابقة.

```text
Feature Branch
      ↓
      PR
      ↓
CI + Review + Verification
      ↓
    Merge
      ↓
    main
```

`main` يبقى نظيفًا، واضحًا، وقابلًا لأن يكون نقطة انطلاق لأي تطوير لاحق.

### المرحلة 14 — Production Deployment

بعد الدمج، يتم التحقق من Deployment على Production.

يتم التأكد من:

- نجاح Build/Deployment.
- عدم وجود Runtime errors حرجة.
- صحة الاتصال بـ Supabase.
- صحة Authentication.
- صحة الميزة الجديدة.
- عدم حدوث Regression في المسارات الحرجة.

### المرحلة 15 — Smoke Test بعد النشر

تنفيذ Smoke Test مناسب للميزة، مثل:

```text
Login
→ Dashboard
→ Feature
→ Database operation
→ Permission check
→ Logout
```

ويتم تعديل السيناريو حسب نوع الميزة.

**المخرج:** Production Verified.

### المرحلة 16 — التوثيق والإغلاق

بعد نجاح التطوير:

- تحديث الوثائق عند الحاجة.
- توثيق القرارات المعمارية المهمة.
- تسجيل Migrations المهمة.
- تحديث Changelog عند الحاجة.
- التأكد من حالة PR.
- حذف الفرع بعد التأكد من عدم الحاجة إليه، متى كانت صلاحيات GitHub وإجراءات المشروع تسمح بذلك.

**المخرج:** Feature Complete.

## 4. بوابة الجاهزية النهائية

لا تعتبر أي ميزة جاهزة للدمج إلا إذا كانت الإجابات التالية واضحة:

| الفحص | المطلوب |
|---|---|
| بدأت من `main` نظيف؟ | نعم |
| لها Branch مستقل؟ | نعم |
| نطاقها واضح؟ | نعم |
| تم تحليل تأثيرها؟ | نعم |
| التصميم واضح؟ | نعم |
| الاختبارات المناسبة ناجحة؟ | نعم |
| CI ناجح؟ | نعم |
| الأمن وRLS مراجعان؟ | نعم، عند انطباقهما |
| Preview/E2E تم عند الحاجة؟ | نعم |
| Production DB تم تقييمها؟ | نعم، عند وجود تغيير |
| Production deployment ناجح؟ | نعم، عند النشر |
| Smoke test تم؟ | نعم، عند النشر |
| التوثيق مكتمل؟ | نعم، عند الحاجة |

إذا كانت إجابة حاسمة **لا** أو **غير معروفة**، فلا يتم الادعاء بأن الميزة جاهزة.

## 5. قواعد إلزامية عند استخدام ChatGPT في التطوير

عند طلب أي تطوير من ChatGPT، يجب على ChatGPT اتباع هذه الوثيقة أولًا.

### قبل التنفيذ

يجب على ChatGPT:

1. قراءة هذه الوثيقة.
2. قراءة حالة `main` الحالية.
3. فحص الكود الحالي بدل الاعتماد على الذاكرة أو التخمين.
4. تحديد النطاق والتأثير.
5. عدم تكرار أسئلة سبق حسمها أو موجود جوابها في المستودع.

### أثناء التنفيذ

يجب على ChatGPT:

- العمل على Feature Branch مستقل.
- الحفاظ على نطاق التغيير.
- إظهار الفشل الحقيقي وعدم إخفائه.
- عدم تغيير Production دون سبب مقصود ومحدد.
- عدم فرض تغييرات غير مرتبطة بالطلب.
- عدم الكتابة فوق تاريخ `main` أو إعادة ضبطه دون تفويض صريح وسبب واضح.
- عدم استخدام فرع قديم كأساس لتطوير جديد دون فحص.

### قبل الدمج

يجب على ChatGPT التحقق من:

- الاختبارات.
- TypeScript / Build.
- Security.
- RLS / Tenant isolation عند انطباقها.
- Migration safety عند انطباقها.
- Preview / E2E عند الحاجة.
- حالة Production Deployment عند النشر.

### إذا ظهر خطأ أو تعارض

لا يتم الاستمرار وكأن كل شيء سليم.

يجب:

1. تحديد السبب.
2. تحديد نطاق الأثر.
3. إصلاح السبب أو عزل المشكلة.
4. إعادة تشغيل التحقق المتأثر.
5. تسجيل أي قرار مهم.

## 6. قاعدة منع الخربطة

هذه القواعد غير قابلة للتجاوز إلا بقرار صريح وموثق:

1. `main` ليس مكان التطوير.
2. كل ميزة لها Branch واضح.
3. كل ميزة لها PR واضح.
4. لا دمج بدون CI مناسب.
5. لا تجاهل لفشل أمني أو وظيفي.
6. لا تغييرات Production غير مخططة.
7. لا خلط لأعمال غير مترابطة.
8. لا حذف أو إعادة كتابة تاريخ Git دون ضرورة استثنائية وموافقة صريحة.
9. لا اعتبار العمل مكتملًا قبل التحقق النهائي المناسب.
10. عند الشك، يتم الفحص بدل التخمين.

## 7. تعريف Done في PowerHub

الميزة **Done** عندما تكون:

> **محددة + مصممة + منفذة + مختبرة + مراجعة أمنيًا + متحققة في Preview عند الحاجة + مدمجة بأمان + منشورة عند الحاجة + متحققًا منها بعد النشر + موثقة عند الحاجة.**

## 8. مبدأ الاستمرارية بين جلسات ChatGPT

يمكن أن تستمر أعمال PowerHub عبر جلسات مختلفة. لذلك لا يعتمد التطوير على الذاكرة وحدها.

عند بدء جلسة تطوير جديدة، يجب الرجوع إلى:

1. هذه الوثيقة.
2. حالة `main` الحالية.
3. الـPR أو Issue المرتبط بالمهمة.
4. الملفات الحالية في المستودع.
5. حالة CI وDeployment ذات الصلة.
6. أي وثيقة معمارية أو أمنية مرتبطة بالميزة.

**المستودع هو مصدر الحقيقة للكود؛ وهذه الوثيقة هي مصدر الحقيقة لدورة التطوير باستخدام ChatGPT.**
