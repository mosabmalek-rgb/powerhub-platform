# تصميم إنشاء اشتراك صاحب المولد عبر Supabase

## الوضع الانتقالي

مسارا إنشاء صاحب المولد متوقفان حالياً قبل إنشاء مستخدم في Supabase Auth أو كتابة أي سجل أعمال. السبب أن التنفيذ السابق يجمع بين عملية خارج PostgreSQL (`auth.admin.createUser`) وسلسلة إدخالات PostgREST مستقلة؛ لذلك لا يضمن الذرية أو التعويض الكامل عند فشل خطوة لاحقة.

## الدورة المطلوبة قبل إعادة التفعيل

يُنشأ طلب إنشاء ذو معرف idempotency محفوظ في PostgreSQL أولاً، وتتحقق دالة RPC تحت `pg_advisory_xact_lock` من تفرد البريد والهاتف والرمز ومن صلاحية آدمن المنصة. تسجل الدالة حالة `pending_auth` وتفاصيل الأعمال غير السرية وسجل تدقيق.

بعد نجاح النية، ينشئ الخادم مستخدم Supabase Auth. ثم تستدعي دالة RPC ثانية لإنشاء المستخدم المحلي والمساحة وملف المالك والاشتراك والفرع الأساسي والعضوية وملف الموظف وسجل التدقيق في معاملة واحدة، مع ربطها بمعرف Auth ومعرف الطلب. تفرض الدالة idempotency وتمنع تكرار العناصر عند إعادة المحاولة.

إذا تعذر إنشاء مستخدم Auth فلا تُنفذ معاملة الأعمال. وإذا فشلت معاملة الإتمام بعد إنشاء Auth، يسجل الطلب حالة قابلة للمراجعة ويبدأ تعويضاً صريحاً لحذف مستخدم Auth الذي أنشأه الطلب فقط؛ لا يُحذف مستخدم قائم. إذا تعذر التعويض، يبقى الطلب `needs_reconciliation` ولا يعاد إنشاء حساب ثانٍ.

## متطلبات إعادة التفعيل

لا يعاد التفعيل قبل تطبيق migrations للدالتين وتحقق وجودهما في Supabase، واختبارات عزل تمنع MySQL، واختبار تعارض يعيد المحاولة بالـ idempotency نفسه، ومراجعة تشغيلية لا تستخدم أي حساب أو مستأجر إنتاجي من دون موافقة وخطة تنظيف.
