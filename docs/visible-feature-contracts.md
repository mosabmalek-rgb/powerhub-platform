# Visible Feature Contract — PowerHub

القاعدة الأساسية:

> **لا يجوز أن تكون هناك وظيفة أو ميزة أو زر أو عملية ظاهرة للمستخدم تبدو قابلة للتنفيذ ثم تبدأ العملية وتفشل لأنها غير موصولة بمسار حي، أو تعتمد على إجراء متقاعد، أو تترك حالة جزئية غير مفهومة.**

## 1. تعريف العملية الحية

تُعتبر العملية Live فقط عندما تكون السلسلة التالية مكتملة ومتحققة:

`UI action → client procedure → server authorization → Supabase/RPC → state change → response → UI reconciliation`

ويجب أن يكون الفشل في أي مرحلة:
- صريحاً للمستخدم.
- قابلاً للفهم.
- دون رسالة نجاح كاذبة.
- ودون ترك حالة جزئية غير معلومة.

## 2. ما يجب أن يكون مخفياً

أي عنصر لا يملك مساراً إنتاجياً حياً يجب ألا يظهر كإجراء قابل للتنفيذ، مثل:
- الإجراءات المتقاعدة.
- الإجراءات غير الموصولة بخلفية فعلية.
- الميزات المؤجلة التي لم يعتمد تشغيلها بعد.
- الأزرار التي تبدأ مساراً معروفاً بالفشل أو تعيد `PRECONDITION_FAILED` دائماً.
- أدوات الاختبار أو الـShowcase غير المقصودة للمستخدم النهائي.

## 3. حالات الفشل التي يجب منعها

### False Success
لا تعرض الواجهة نجاحاً قبل التأكد من نجاح العملية الأساسية.

### Start-then-fail
لا يبدأ الإجراء إذا كان شرطه الأساسي معروفاً مسبقاً بأنه غير متوفر.

### Partial Commit
عند وجود خطوات خارج المعاملة، يجب وجود:
- تعويض.
- Intent/Workflow state.
- أو مسار Retry آمن.

### Duplicate Operation
العمليات الحساسة يجب أن تكون idempotent أو محمية بمفتاح/قفل يمنع التكرار.

### Cross-tenant
يجب ألا يؤدي أي ID قادم من العميل وحده إلى تجاوز Tenant أو Site scope.

## 4. مرجع الصلاحيات

كل عملية كتابة أو إجراء حساس يجب أن يتحقق من:
- المستخدم الحالي.
- الدور.
- capability.
- tenant.
- site/branch.
- حالة الحساب.
- حالة الكيان الهدف.
- optimistic/concurrency version عند الحاجة.

ولا تعتبر حماية الواجهة بديلاً عن حماية الخادم.

## 5. قواعد الـUI

الزر الظاهر يجب أن يملك:
- Handler حقيقياً.
- Mutation/Query معروفاً.
- حالة pending.
- حالة error.
- حالة success مبنية على النتيجة الفعلية.
- تحديثاً للبيانات بعد النجاح عند الحاجة.

ويجب ألا تستخدم:
- handlers فارغة لعمليات يفترض أن تكون تشغيلية.
- disabled ثابتاً لزر تشغيلي غير موضح السبب.
- رسائل "تم" قبل نجاح الخادم.

## 6. قواعد Supabase

عند كون Supabase هو المصدر الإنتاجي:
- القراءة/الكتابة يجب أن تمر عبر المسار المعتمد.
- RPC الحساسة تكون محكومة بالصلاحيات.
- لا يعتمد العميل على إجراء متقاعد.
- لا يُسمح للـanon/authenticated باستدعاء وظائف إدارية حساسة دون سياسة صريحة.
- العمليات العابرة للخطوات يجب أن تكون قابلة للاسترداد أو التعويض.

## 7. الاختبارات المطلوبة

كل ميزة تشغيلية جديدة يجب أن تملك، بحسب طبيعتها:
- اختبار المسار الناجح.
- اختبار الرفض/الصلاحية.
- اختبار فشل الخادم.
- اختبار عدم التكرار.
- اختبار Tenant/Site isolation.
- اختبار أن العملية القديمة أو المتقاعدة غير مكشوفة في Runtime UI.

## 8. معيار الإخفاء

عندما تكون ميزة غير جاهزة Production، الخيار الصحيح هو:

**إخفاؤها من الواجهة**

وليس:

**عرض زر يعمل شكلياً ثم يفشل.**

## 9. مراجعة دورية للمنصة

يجب أن تشمل المراجعة الشاملة:
- جميع Routes.
- جميع الأزرار التشغيلية.
- جميع Mutations.
- جميع RPCs المرتبطة بالعمليات الظاهرة.
- الإجراءات المتقاعدة.
- `PRECONDITION_FAILED` المتوقع من واجهات المستخدم.
- TODO/Coming Soon داخل Runtime UI.
- العمليات متعددة الخطوات.
- الرسائل التي تفيد نجاحاً قبل اكتمال العملية.

## 10. الحالة الحالية المعتمدة

الميزات المؤجلة حالياً لا تُظهر مساراتها في واجهة المستخدم.

بالخصوص:
- Owner self-service password recovery من شاشة الدخول: **مؤجلة**.
- Subuser self-service password recovery من شاشة الدخول: **مؤجلة**.

أما تغيير كلمة المرور من داخل الحساب وإعادة التعيين الإداري ضمن الصلاحيات المعتمدة فهما ضمن المسارات الحية الحالية.

## 11. Gate قبل الدمج

لا تعتبر الميزة مكتملة إلا إذا أمكن إثبات:

1. لا يوجد زر تشغيلي ميت.
2. لا يوجد مسار يبدأ ثم يفشل بسبب إجراء متقاعد.
3. لا يوجد False Success.
4. لا يوجد Cross-tenant escape.
5. لا توجد عملية حساسة غير idempotent أو غير محمية بالتزامن.
6. حالة UI بعد النجاح والفشل تعكس حالة الخادم فعلياً.
7. جميع الميزات المؤجلة مخفية عن المستخدم.

هذه الوثيقة هي معيار التدقيق العام لـPowerHub في مراجعات Visible Feature Contracts القادمة.
