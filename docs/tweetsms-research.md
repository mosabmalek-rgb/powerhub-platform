# ملاحظات تحقق TweetSMS

تمت مراجعة الموقع الرسمي لخدمة TweetSMS في 23 أغسطس 2026. تؤكد الصفحات الرسمية توفر **بوابات API للمبرمجين**، و**نظام حسابات فرعية**، وتقارير تسليم وإرسال SMS للمؤسسات، بما يتوافق مع النموذج الإداري المعتمد في PowerHub.

## Tweet JSON API

وثيقة Tweet JSON API العامة تستخدم طلبات `POST` مع ترويسة `Content-Type: application/json`، وتعتمد مفتاحاً واحداً في جسم الطلب باسم `api_key`.[1]

| العملية | المسار الرسمي | جسم الطلب المعروف | أكواد الاستجابة الموثقة |
|---|---|---|---|
| التحقق من الحساب | `https://www.tweetsms.ps/api.php/office/chk_user` | `{ "api_key": "…" }` | `999` نجاح؛ `-100` معلمات ناقصة؛ `-111` غير مفعّل؛ `-112` محظور؛ `-110` مفتاح غير صحيح |
| الرصيد | `https://www.tweetsms.ps/api.php/office/chk_balance` | `{ "api_key": "…" }` | `999` استرجاع الرصيد بنجاح؛ `-100` معلمات ناقصة؛ `-110` مفتاح غير صحيح |

تتضمن الوثيقة أيضاً عمليات `sendsms` و`send var sms`، لكنها لم تعرض بعد حقول الطلب أو مثال الاستجابة في العرض الأولي؛ ستستخرج من وثيقة الإرسال الثانية أو من عناصر هذه الوثيقة بالتفصيل قبل كتابة العميل.

## TWEETSMS API — API-KEY

تعرض وثيقة API-KEY مساراً موازياً يستخدم `POST` مع `Content-Type: application/x-www-form-urlencoded` ويضع `api_key` في الجسم. يظهر مسار التحقق في `https://tweetsms.ps/api.php/maan/chk_user`، ومسار الرصيد في `https://tweetsms.ps/api.php/maan/chk_balance`.[2]

> تعرض الوثيقة أمثلة مفاتيح ورموز. تعامل PowerHub معها على أنها أمثلة عامة فقط ولا يحفظها أو يستخدمها. يقبل النظام المفاتيح الخاصة بالحساب الفرعي من آدمن المنصة وحده ويشفرها عند الحفظ.

تطلب واجهة الرصيد في هذا المسار `api_key` و`token` في نموذج URL-encoded، وتعرض الوثيقة ترويسة `X-Auth-Token`. لا توضح أمثلة الاستجابة المهيكلة أو حقول مسار `sendsms` في العرض المكتشف حتى الآن؛ لذلك سيستخدم التطبيق عقداً مرناً للردود ويمارس إرسالاً حياً فقط بعد تأكيد الحقول التفصيلية لمسار `sendsms`.

مسار الإرسال المفرد/الجماعي الموثق هو `POST https://tweetsms.ps/api.php/maan/sendsms` مع `Content-Type: application/x-www-form-urlencoded`.[2] الحقول المعروفة هي `api_key` و`sender` و`message`، وتقبل `to` قائمة أرقام مفصولة بفاصلة. يدعم المزود حقلي `groups` و`date` و`time` اختيارياً، ولن تستخدمها PowerHub في الإرسال الفوري.

| النتيجة | الدلالة وفق الوثيقة | معالجة PowerHub |
|---|---|---|
| `999` | إرسال ناجح | وسم الرسالة `submitted` وتسجيل استجابة المزود |
| `-100` | حقل مطلوب ناقص | فشل إعداد؛ لا إعادة محاولة تلقائية |
| `-111`, `-112`, `-114` | حساب غير مفعّل أو محظور أو إيقاف إرسال | فشل إعداد؛ ينبه آدمن المنصة |
| `-115`, `-116`, `-117`, `-118` | اسم مرسل غير صالح أو غير نشط/مرفوض | فشل إعداد؛ يراجع آدمن المنصة اسم المرسل |
| `-124` | رصيد TweetSMS غير كافٍ | فشل مؤقت مع تحديث رسالة توضح الرصيد |
| `-126` | لا يمكن الإرسال حالياً | فشل مؤقت قابل لإعادة المحاولة |

## تقارير التسليم

تعرض وثيقة API-KEY عمليات باسم `get_archive` و`message details`، لكن العرض العام لا يوضح حقول الطلب أو نموذج حالة التسليم أو Webhook/Callback. كما لم يُظهر البحث العام مرجعاً رسمياً من TweetSMS لدعم Webhook لتقارير التسليم.

لذلك سيحتفظ PowerHub بمسار استقبال داخلي آمن ومتحقق منه لتحديثات التسليم عندما يزود TweetSMS رابط Callback الرسمي، وسيعتمد حتى ذلك الحين على حالة الإرسال التي يعيدها المزود وسجل الرسائل المحلي؛ لن يُفعّل أي استعلام دوري افتراضي أو ادعاء بتسليم نهائي دون عقد موثق.

أعيدت مراجعة رابط Postman نفسه لقسم `get_archive` في 23 أغسطس 2026، لكن العرض العام لم يحمّل حقول العملية أو نموذج استجابة إضافياً بعد محاولة إعادة التحميل. لا يغيّر ذلك القرار: لا يمكن بناء مزامنة تسليم صحيحة من اسم العملية فقط.
