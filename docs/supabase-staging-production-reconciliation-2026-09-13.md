# مصالحة Supabase بين staging وProduction — 2026-09-13

## النطاق

تمت مقارنة بيئة `powerhub-staging-dr` مع Production `vvcdiqcyhaloxesvpppc` قراءةً فقط. لم تُطبق migrations أو SQL تعديلي على Production، ولم تُنقل بيانات أعمال أو أسرار بين البيئتين.

## النتيجة البنيوية

بيئة staging ليست نسخة كاملة أو أحدث من Production؛ بل تختلف عن Production في خط الترحيل والمخطط والـRPCs. أظهر الجرد أن staging تحتوي على 51 migration و46 جدولاً، بينما Production تحتوي على 90 migration و58 جدولاً. كما أن قوائم الدوال العامة غير متطابقة: توجد وظائف تشغيلية في Production لا تظهر في staging، والعكس صحيح. لذلك لا يجوز نسخ migrations المفقودة آلياً أو اعتبار staging مرجعاً مباشراً للدمج.

## نتيجة فرع PR #37

نجح `pnpm check` بعد إصلاح أخطاء TypeScript في الواجهات المتأثرة. لكن `pnpm test` لم ينجح: مرّ 225 اختباراً وفشل 19 اختباراً في 4 ملفات من أصل 63 ملف اختبار. تتركز الإخفاقات في إجراءات Supabase الإدارية غير المكتملة أو التي ما زالت تشير إلى `retiredMutation`، ومنها حفظ وفحص حساب TweetSMS المركزي، تغيير حالة مساحة صاحب المولد، وإثراء بيانات طلبات ترقية الاشتراك، إضافة إلى قراءات مركزية أخرى ما زالت مرتبطة بعقد سابق.

## القرار الآمن

لا يُشغّل AST retirement، ولا يُدمج PR #37، ولا يُنشر Production قبل استكمال عقود Supabase الفعلية أو تحديث الاختبارات فقط بعد اعتماد عقود بديلة مطابقة للسلوك المطلوب. إصلاح TypeScript وحده لا يثبت اكتمال الترحيل.
