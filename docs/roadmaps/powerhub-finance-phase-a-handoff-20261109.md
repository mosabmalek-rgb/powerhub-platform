- تم إضافة `serviceRecognition.requiredInvoiceMonths` و`serviceRecognition.missingGL` للأشهر المنتهية بتوقيت غزة؛ لا تُعتبر الفاتورة وحدها دليلاً على أن إيراد الخدمة المكتسب رُحّل. يدخل عدد المفقود إلى `unreconciledSourceCount`.
- اختبار Staging داخل تراجع: قبل قيود الاعتراف كان `missingGL=3` في أكتوبر؛ بعد الاعتراف بثلاث فواتير أصبح `missingGL=0`. لا تظهر بيانات اختبارية بعد `ROLLBACK`.
### 17000 — إيراد الخدمة الفعلي عن أشهر مكتملة
- `powerhub_financial_gl_recognize_billed_service(tenant,site,invoice,period,actor)`: بعد اكتمال الشهر بتوقيت غزة فقط، ومن قيد فاتورة مُرحّل بالإيراد المؤجل، ينقل مبلغ أيام الخدمة بأصغر وحدة نقدية من مدين 2200 إلى دائن 4100، بدون double count أو إيراد غير مفوتر تخميني.
- يدعم إعادة المحاولة، ويمنع شهر غير مكتمل أو دورة غير صحيحة أو فاتورة غير مرحلة أو مبلغ صفر.
- اختبار Staging أكتوبر أعطى 2,621.50 بعد جمع ثلاث فواتير، وتطابق مع تقرير توزيع الخدمة؛ نوفمبر غير المكتمل رفض الاعتراف.

## 6. موانع قبول المحاسبة النهائية
1. لا ترحيل دائم لـ15000–17000 حتى نجاح CI والمراجعة ثم مسار Staging المحمي.
2. لا يوجد رصيد افتتاحي حقيقي معتمد أو قيود GL دائمة في Staging عند آخر فحص؛ البيانات الاختبارية وحدها لا تعادل قبول المحاسبة الحقيقية.
3. شراء المورد رقم 8 ما زال `confirmed` دون `purchase_receipt` موثق، لذلك يُرفض اعتباره مخزوناً مستلماً. يمكن توليد حالة اختبارية مكتملة عبر workflow المشروع لا بتغيير حالة الشراء فقط.
4. منظومة الحسابات/المخزون/الموردين تحتاج تسوية آمنة للمراجع التاريخية، ويجب دراسة الحركات ذات المراجع الاختبارية في سياق العزل.
5. ربط استحقاق الرواتب وصرفها اختبر ضمن معاملات لكن لا يوجد تقييم شامل لكل السيناريوهات المالية الحية عبر واجهة المستخدم.
6. الإقفال والتقارير النهائية وقائمة دخل معتمدة ومركز مالي متوازن حقيقي وربحية الفروع والمقارنات والتصدير المهني لا تزال بوابات مرحلة 2/3.
7. لا دمج PR قبل مراجعة أداء Staging، الصلاحيات والتزامن، UI Preview وVercel، وحماية مصدر وثبات سجل التدقيق.

## 7. ترتيب الاستئناف المقترح
1. اقرأ أولاً GitHub PR #359 الحالي SHA وCI الأربع، ونسخ SQL 15000–17000 واختبارات source coverage، ثم سجل Staging.
2. أغلق فشل CI إن وجد (خاصة coverage recognition وPayroll settlement في اختبار مستقل).
3. افحص ثبات المصدر بعد الترحيل، ومطابقة المستند مع السطور، وسلوك قيود الاستحقاق/العكس والحسابات المقابلة وماليات العملاء.
4. وثّق موافقات Staging، ثم نفّذ 15000 و16000 و17000 بالتسلسل عبر المسار المحمي وبأرقام النسخ الأصلية. لا تعتمد نتيجة المعاملة التجريبية بديلاً عن اختبار ما بعد الترحيل.
5. أنشئ بيانات اختبارات Staging شاملة بمرجع واضح، واختبر عبر RPC وtRPC ومستخدمين مختلفين مع ضمان عدم حدوث إدخالات مزدوجة، ثم طبّق تقارير التغطية والميزان في أشهر متعددة.
