# خطة PowerHub لمصادقة مستدامة وتهيئة الجهاز الأول (First-Login Bootstrap)

- **الحالة:** خطة تنفيذ موثقة على `main`؛ لا تعني أن جميع المراحل منفذة أو أن الدخول دون اتصال اجتاز اختبار متصفح حي.
- **تاريخ التوثيق:** 2026-10-26
- **تحديث الحالة:** أكد المشغّل أن مشكلة الدخول وحلقة التوجيه حُلّت في الاستخدام الفعلي. هذا لا يغلق اختبارات إعادة فتح المتصفح أو العمل دون اتصال أو Delta أو مراقبة refresh.
- **PR التنفيذ الموحد:** `feat/auth-local-first-single-pr` يجمع تغييرات بدء Local-First، وتهيئة الكاش، وبوابات المصادقة، والاختبارات الرجعية في PR واحد. تبقى المراحل مفتوحة حتى اجتياز بواباتها.
- **نقطة الأساس:** `a2612a00843a51826ec5e64e70029aada1d35371` (دمج PR #357).
- **صلة الخطة:** [خطة Local-First + Delta Sync الرئيسية](../p7-offline-first-delta-sync-roadmap.md).
- **هدف المستخدم:** فتح مساحة العمل بسرعة من جلسة محفوظة، إظهار آخر البيانات المحلية المسموح بها، منع حلقات التوجيه وطلبات المصادقة المتكررة، تهيئة الجهاز الأول مرة واحدة، والحفاظ على كل عملية غير متزامنة إلى أن تُسوّى أو يطلب المستخدم حذفها صراحةً.

## 1. الملخص التنفيذي والقرارات المعمارية

تُنفَّذ الخطة على مراحل صغيرة، مع بوابة اختبار وقياس لكل مرحلة. المصدر النهائي للهوية والصلاحية وبيانات العمل هو Supabase/PostgreSQL والخادم؛ البيانات المحلية نسخة عرض/عمل محلية مقيدة وليست بديلًا عن التحقق الخادمي أو قفل الجهاز أو RLS.

### قرارات ملزمة

1. **عميل مصادقة واحد:** يبقى عميل Supabase في `client/src/lib/supabase.ts` هو العميل المشترك. يظل SDK مالك دورة تجديد الرموز الطبيعية؛ لا نعيد إدخال استدعاءات `refreshSession()` اليدوية أو تدوير refresh token من عدة مسارات.
2. **لا رموز مكررة في مخازن مخصصة:** يستخدم التطبيق استمرار جلسة Supabase الذي يملكه SDK (`persistSession: true`). لا ينسخ access token أو refresh token إلى مفاتيح LocalStorage خاصة بـPowerHub. يمكن حفظ *ملخص سياق غير سري* وبيانات الكاش، لكن لا يصبح هذا الملخص إثبات صلاحية.
3. **لا قاعدة عمل محلية موازية:** خط الأساس يستخدم IndexedDB أصليًا، لا Dexie.js. قاعدة `powerhub-offline-workspace` هي مخزن العمل التشغيلي المشترك (الإصدار 4)، بينما الكاش والمصادقة في مخازن منفصلة. **لا نضيف Dexie ولا ننقل الجداول إليه ضمن هذه الخطة تلقائيًا**؛ إضافة طبقة ثانية الآن ترفع خطر ازدواج الطوابير وفقد العمليات. إذا كان اعتماد Dexie شرطًا غير قابل للتغيير، يُفتح ADR مستقل أولًا مع خطة ترحيل قابلة للعكس.
4. **عرض محلي سريع، لا تجاوز للمصادقة:** يمكن إظهار snapshot محلي بسرعة عند وجود جلسة/رخصة offline صالحة وكاش لنفس الحساب والنطاق. لا يجوز استخدام الكاش لتمرير طلب tRPC محمي دون Access Token صالح أو لمنح دور/مستأجر/فرع غير متحقق منه.
5. **لا تعهد حرفي بـ0ms:** IndexedDB غير متزامن ويحتاج قراءة فعلية؛ الوعد القابل للقياس هو عرض آخر snapshot فور اكتمال القراءة المحلية، من دون انتظار الشبكة. يقاس الزمن بدل ادعاء زمن صفري حرفيًا.
6. **الحفاظ على العمل يتقدم على التنظيف الصامت:** لا يجوز حذف Outbox أو المسودات غير المزامنة عند تسجيل الخروج لمجرد أنها «بيانات تشغيل». يسحب الخروج الجلسة ويمنع عرض بيانات الحساب؛ تبقى العمليات المعلقة معزولة ومقفلة على هوية صاحبها حتى يعاود تسجيل الدخول أو يزامنها/يصدّرها/يؤكد حذفها صراحةً. حذفها تلقائيًا يتناقض مع شرط Zero Data Loss.
7. **لا تهيئة شبكة جديدة تنافس Delta Sync:** `bootstrapDeviceContext` سيكون منسقًا idempotent فوق APIs والتخزين ومحرك Delta/Outbox الموجودين، لا محرك مزامنة ثانٍ ولا نسخًا مستقلة من قواعد الأعمال.

## 2. خط الأساس الفعلي في المستودع

| المجال | الوضع المثبت في الكود | النتيجة المطلوبة |
|---|---|---|
| جلسة Supabase | `client/src/lib/supabase.ts` ينشئ عميلًا واحدًا باستخدام `persistSession` و`autoRefreshToken` و`detectSessionInUrl`؛ توجد قراءة جلسة محدودة المهلة ومسار تشخيص/تهدئة | مالك واحد لدورة الجلسة، قراءة مشتركة محدودة، وتعافٍ بلا سباقات/عواصف refresh |

| سياق الواجهة | `AuthProvider/useAuth` موجود، ويكشف المستخدم وحالة الجلسة/المصادقة والتحميل والخطأ؛ سياق المستأجر/الفرع وbootstrap readiness ليسا عقدًا مركزيًا مكتملًا | إضافة `tenantId/siteId/deviceId/isBootstrapped/bootState` كمخرجات واضحة ذات مصدر موثوق |

## 3. عقد الحالة المركزي (Auth + Device Context)

ينشأ عقد TypeScript واحد، من خلال `AuthProvider/useAuth` أو وحدة سياق مشتركة مستخدمة داخله، ويكون على الأقل:

```ts
type BootState =
  | "initializing"
  | "restoring-local"
  | "validating-online-session"
  | "resolving-organization"
  | "bootstrapping-device"
  | "ready"
  | "offline-ready"
  | "needs-login"
  | "recoverable-error";

type AuthDeviceContext = {
  user: AuthenticatedPowerHubUser | null;
  tenantId: number | null;
  siteId: number | null;
  deviceId: string | null;
  isAuthenticated: boolean;
  isBootstrapped: boolean;
  isLoading: boolean;
  bootState: BootState;
  isOnline: boolean;
  lastSyncedAt: string | null;
  refresh(): Promise<void>;
  logout(): Promise<void>;
};
```

هذا العقد توضيحي؛ أنواع المستخدم/الموقع يجب أن تطابق أنواع المشروع الفعلية ولا تُنسخ الأنواع بشكل يدوي متضارب.

### قواعد جاهزية الطلبات

- يُسمح بالاستعلامات العامة واللازمة لإكمال المصادقة والتهيئة فقط قبل اكتمال السياق.
- لا تبدأ استعلامات بيانات مجال محمية قبل وجود جلسة online قابلة للاستخدام أو حالة `offline-ready` بكاش صالح، وحل `deviceId`، وحل `tenantId/siteId` المسموح بهما.
- **حالة offline لا تعني أن tRPC authenticated.** عند غياب Access Token صالح، لا ترسل أي طلب محمي؛ استخدم القراءة المحلية والطابور فقط.
- كل طلب محمي online يحمل `Authorization: Bearer <access_token>` و`x-powerhub-device-id`. لا يعتبر `tenantId/siteId` القادم من المتصفح مصدر صلاحية؛ يعيد الخادم حل الصلاحيات ونطاق الفرع ويتحقق من قفل الجهاز.
- لا يعاد استخدام Query Cache أو cursor أو grants عند تبديل user/tenant/site/device؛ كل مفتاح محلي وكل سجل تشغيل يقيّد على الهوية والنطاق الكاملين.
- الأخطاء العابرة تُعرض بوصفها تعافيًا قابلًا لإعادة المحاولة، ولا تحول إلى تسجيل خروج ضمني. الرفض الصريح/إبطال الصلاحية يبقى قرارًا مختلفًا.
- لا يوجد redirect إلى `/login` طالما أن state machine في مرحلة استعادة محلية/تحقق محدود أو يوجد خطأ قابل للتعافي؛ تنتهي كل مرحلة بحد زمني وحالة مرئية.

## 4. دورة الجلسة المستدامة

### عند التشغيل أو إعادة فتح المتصفح

1. اقرأ الحالة المحلية والرخصة وملخص المستخدم/النطاق من مخازنها الحالية، بقراءات محدودة المهلة.
2. إذا كان المتصفح يبلغ صراحةً أنه offline، وكانت الرخصة صحيحة وغير منتهية، والملف الشخصي والـsnapshot يعودان لنفس المستخدم والنطاق، فاعرض `offline-ready` من دون طلبات شبكة عند الإقلاع. يجب ألا تستدعي تهيئة هذا المسار `auth.me` أو tRPC محميًا.
3. إذا كان الاتصال محتملًا، ابدأ فحص الاتصال والمصادقة بصورة غير حاجبة لعرض shell المحلي. ينتظر حارس التوجيه نتيجة أول probe فقط عندما يكون هناك snapshot ورخصة Offline صالحة؛ لا يعلّق المستخدم العادي ولا يبدأ حلقة redirect.
4. عند وجود جلسة Supabase صالحة، تحقق من `auth.me` ومن سياق المستخدم/المستأجر/الموقع/الجهاز قبل عرض واجهة online المصادق عليها.
5. عند تعذر الشبكة مؤقتًا، احتفظ بالـsnapshot المحلي والرخصة الصالحة واعرض حالة Offline/آخر مزامنة؛ لا تعتبر ذلك نجاحًا جديدًا لمصادقة الخادم.
6. عند انتهاء الرخصة أو فقدان المفتاح/تلف السجل، لا يتجاوز التطبيق بوابة المصادقة ولا يستنتج هوية المستخدم من مفتاح LocalStorage قابل للتعديل؛ يعرض شاشة دخول/استعادة واضحة.

### عند عودة الشبكة

- يستخدم SDK دورة التجديد الطبيعية؛ لا توجد مهمة refresh مستقلة لكل صفحة أو tab.
- عند تأكيد `TOKEN_REFRESHED`، ترفع حالة readiness وتعيد محاولة الاستعلامات النشطة التي فشلت بسبب غياب token، مع قفل/تهدئة تمنع عاصفة طلبات.
- بعد نجاح التحقق الخادمي، يعاد حل سياق الصلاحية وتنفذ Delta من cursor المحفوظ، ثم تتحدث caches/الكيانات المتأثرة فقط.
- إذا تبدلت هوية المستخدم أو رفض الخادم الجلسة صراحةً، تُلغى الطلبات القديمة وتُمنع عمليات الكتابة المحلية التي تعود للسياق السابق.

### تمييز الإغلاق عن الخروج

- إغلاق تبويب/متصفح أو إعادة تحميل الصفحة ليس حدث تسجيل خروج: لا تمسح الجلسة التي يديرها Supabase SDK، ولا الـOutbox، ولا الـcursors أو snapshots.
- تسجيل الخروج الصريح يمسح جلسة Supabase المحلية، والرخصة المحلية، وملخص المصادقة، وكاش الاستعلامات الحساسة للمستخدم، وحالة الذاكرة/QueryClient، ويحرر قفل الجهاز خادميًا ضمن مهلة محددة.
- إذا كان هناك Outbox معلّق، فالسلوك الافتراضي الآمن هو إبقاؤه معزولًا ومقفلًا إلى المستخدم الأصلي حتى تتم مزامنته أو تصديره/التخلص منه بتأكيد صريح. لا يُعرض للمستخدم التالي. لا يحذف Logout المسودات بصمت؛ ذلك وحده هو ما يحقق Zero Data Loss.
- يظل logout محليًا ناجحًا حتى لو تأخر تحرير قفل الجهاز بسبب الشبكة؛ تُسجل حالة تحرير القفل كعملية استرداد قابلة لإعادة المحاولة ولا تؤخر إزالة التوكن المحلي.

## 5. التهيئة الأولى: `bootstrapDeviceContext`

تكون عملية منسقة مرة واحدة **لكل** مركب هوية:
`userId + tenantId + siteId + deviceId + localSchemaVersion + bootstrapVersion`.
لا تكتفِ بعلامة Boolean عامة مشتركة بين الحسابات أو الفروع.

### تسلسل bootstrap المقترح

1. **Prerequisites:** الجلسة online نجحت و`auth.me` أعاد user معروفًا؛ معرّف الجهاز UUID ثابت؛ حل الخادم المستأجر/الموقع وقدرة المستخدم على الوصول إليهما. لا تنفيذ لهذا التسلسل لأول مرة إذا كان offline؛ يعمل offline فقط ما سبق تهيئته.
2. **Acquire/recover local record:** أنشئ سجل `bootstrapState` scoped مع `bootstrapVersion` و`schemaVersion` و`requestId` وtimestamps وحالة كل خطوة. إذا بدأ bootstrap سابقًا ثم توقف، استأنف الخطوات الناقصة بدل التكرار.
3. **Tenant/site metadata:** احصل على بيانات السياق عبر الاستعلامات والصلاحيات الحالية؛ لا تنسخ memberships أو الأدوار إلى مصدر صلاحية محلي. خزّن أقل metadata لازمة للعرض السريع مع `lastValidatedAt`.
4. **Device/range provisioning:** احصل على `deviceId` الدائم ثم استعمل `powerhub.offlineNumbering.reserve` الموجود لحجز grants اللازمة للمستخدم المخول (مثل نطاق المشتركين العام ونطاق فواتير السنة المناسبة). استخدم request ID ثابتًا لاستئناف نفس الطلب، وتحترم الحصة والدور وقفل الجهاز؛ لا يفشل فتح مساحة العمل بالكامل إذا كان الحجز غير مطلوب أو ممنوعًا لدور المستخدم.
5. **Initial snapshot/cursors:** للكيانات التي يدعمها محرك Delta، احصل على baseline/cursor ثابت وادمج الصفحة الأولى بحدود صفحات واضحة. لا تعتمد cursor نهائيًا قبل حفظ كل عناصر الصفحة الملتزمة. للكيانات التي لم تدخل Delta بعد، استخدم استعلامها الحالي المصرح به كحل مؤقت ومعلن، دون بناء محرك تنزيل جديد؛ تتم إضافتها لاحقًا لخطة تغطية Delta.
6. **Commit local readiness:** سجل نتيجة كل خطوة بعد نجاحها. تكون علامة `isBootstrapped=true` فقط بعد حفظ السياق اللازم والـbaseline/cursors والـgrants المطلوبة بحسب الدور/المجال، أو قرار موثق بأن خطوة اختيارية غير لازمة. تحفظ العلامة داخل النطاق الصحيح، لا في global LocalStorage.
7. **Steady-state:** بعد نجاح bootstrap الأول، تتوقف عملية bootstrap عن سحب البيانات في كل تشغيل. تُدار كل تغييرات البيانات التالية عبر Outbox/Delta Sync القائم؛ يستأنف التطبيق من cursor ويحصل على الفروق فقط.
8. **Failure/recovery:** لا تُكتب علامة اكتمال عند partial failure. لا يعاد إنشاء grants أو سجلات الكيانات بلا idempotency. تعرض الواجهة الخطوة القابلة لإعادة المحاولة، مع إبقاء snapshots السابقة سليمة.

### invariants

- `bootstrapDeviceContext` idempotent: تشغيله مرتين بالـscope والـrequest IDs نفسيهما لا يخلق نطاق أرقام ثانٍ ولا يكرر كيانًا.
- `isBootstrapped` محلي ومقيّد بالنطاق وإصدار المخطط/التهيئة.
- تغيير user/tenant/site/device أو bootstrap/schema version لا يثق بالعلامة القديمة؛ يتحقق من السياق ويستأنف migration/bootstrap المناسب.
- لا يكتب bootstrap مباشرة إلى عدة caches منفصلة كأنها مصادر حقيقة؛ writes التشغيلية تمر عبر IndexedDB الموحد والـAPIs المعتمدة، ويحدّث TanStack Query من نتيجة محفوظة/معروفة.
- bootstrap ليس شرطًا لحذف/إعادة إنشاء بيانات موجودة، ولا يجري full refresh في كل login.

## 6. قاعدة الترحيل المحلي غير التدميرية

قبل بناء أي ترحيل، أنشئ inventory فعليًا لمخازن IndexedDB والأسماء والإصدارات والمفاتيح والفهارس ومصادر كتابة البيانات. لا تفترض أن كل جهاز يحمل نفس المخطط.

### المخازن المعروفة حاليًا

- `powerhub-offline-workspace` — الإصدار 5، قاعدة العمليات/numbers/Delta/field readings الحالية ونقطة حفظ `bootstrapState` المقيّدة بالنطاق.
- `powerhub-offline-cache` — الإصدار 2، كاش TanStack Query وملخصات المستخدم.
- `powerhub-offline-auth` — الإصدار 1، رخصة Offline ومفتاح HMAC ومعرّف الجهاز.
- بالإضافة إلى أي مخازن legacy/field-reading ظهرت في إصدارات سابقة؛ يحدد الاسم/الإصدار من الكود الفعلي والاختبارات قبل اختيار التحويل.

### بروتوكول safe migration

1. **Inventory/checkpoint:** احفظ `sourceDatabase`, `sourceVersion`, `targetVersion`, migration ID، counts، ومفاتيح السجلات قبل البدء.
2. **Copy then validate:** انسخ إلى target مع الحفاظ على PK/UUID و`clientOperationId` و`dependsOn` وuser/tenant/site/device وpayload والحالة ومحاولات retry وnextAttemptAt/cursor/tombstone. لا تمسح المصدر في نفس الخطوة التي تنسخ فيها البيانات.
3. **Idempotency:** نفس migration ID لا يكرر عناصر target. إذا وجد المفتاح نفسه ومحتوى مختلف، لا تكتب فوقه عميانيًا؛ ضع تعارضًا في quarantine مع السبب.
4. **Validate:** قارن عدد السجلات ومجموع المفاتيح ووجود العمليات المعلقة وسلامة روابط الاعتماديات؛ اختبر عينة payload/checksum حيث ينطبق. عطل migration إذا ظهر نقص غير مفسر.
5. **Quarantine not discard:** السجلات القديمة غير محددة النطاق أو غير القابلة للتحليل تُحفظ في quarantine قابلة للتشخيص/التصدير، ولا تُعرض لغير مالكها ولا تُحذف تلقائيًا.
6. **Cutover:** حوّل القراءات/الكتابات إلى target بعد نجاح validation فقط. يظل المصدر محفوظًا لإصدار/فترة رجوع معروفة، ولا يمحى إلا بسياسة تنظيف منفصلة، بعد التأكد من عدم وجود عمليات معلقة وأن الاسترجاع متاح.
7. **Interrupted browser close:** إذا أغلق المستخدم المتصفح أثناء الترحيل، تستأنف الخطوة التالية من checkpoint. لا يعتمد النجاح على بقاء tab مفتوحًا ولا تُعتبر عمليات الذاكرة وحدها دليلًا على الحفظ.
8. **Schema upgrade:** إذا كان target version أحدث، تعالج الترقية ضمن `onupgradeneeded`/المعاملة الملائمة مع فحص التوافق. لا تفتح عدة مكونات النسخة نفسها بمنطق إنشاء متعارض للمخازن.

## 7. Delta Sync وTanStack Query: من المسؤول عن ماذا؟

- **Outbox:** يستقبل أي عملية Offline مسموح بها مرة واحدة بمعرّف `clientOperationId` ثابت. لا تتغير الهوية عند retry.
- **Server mutation:** يطبق authorization + idempotency + قواعد المجال + audit، ويعيد النتيجة النهائية. العمليات المالية/اعتمادات القراءات الحساسة لا تصبح نهائية لمجرد أن لها نسخة محلية.
- **Delta:** يبقى صاحب المزامنة اللاحقة والتغييرات الخارجية، مع cursor ثابت scoped للـuser/tenant/site/entity ومعالجة tombstones.
- **Local database:** مخزن تشغيل مستدام، مع تحديث cursor والكيانات/التغييرات في معاملات متسقة قدر الإمكان. لا تكتب cursor بعد العناصر التي يمثلها قبل التأكد من حفظها.
- **TanStack Query:** طبقة وصول/عرض وتنسيق freshness/invalidation؛ لا تكون مصدرًا ثانيًا للعمليات. بعد mutation أو Delta، تحدث الاستعلامات المتأثرة من النتيجة المحلية/الخادمية وتجنب invalidating كل QueryClient.
- **Bootstrap:** ينشئ baseline فقط ثم ينتهي؛ لا يعيد تنزيل full snapshot في التشغيل التالي إلا لأول مزامنة، أو فقد cursor/schema corruption، أو طلب full reconcile موثق.
- **نطاق التغطية:** لا يعلن المجال مدعومًا بالكامل إلا بعد اختبارات له. المجالات المالية، الموارد البشرية، الصلاحيات، الأرصدة، والإعدادات الحساسة قد تظل live-only أو read-only Offline بحسب policy لكل procedure.

| AUTH-03 | فتح tab ثانٍ مع انتهاء Access Token | لا عاصفة refresh ولا revoke نتيجة race؛ لا token فارغ يمر للطلبات المحمية |
| AUTH-04 | انتهاء المهلة/خطأ Auth مؤقت | شاشة تعافٍ واضحة، لا redirect loop ولا clear cache للخطأ العابر |
| CTX-01 | user لديه فروع/tenant متعدد | لا يبدأ تحميل البيانات حتى يحل النطاق؛ لا يخلط بيانات أي نطاق آخر |
| OFF-01 | فتح المتصفح وهو offline والرخصة/الكاش صالحان | يعرض snapshot بعد قراءة محلية؛ صفر طلبات شبكة أثناء الإقلاع في هذا المسار |

| OFF-03 | الرخصة منتهية أو مفتاح HMAC مفقود | لا استعادة غير مصرّح بها؛ رسالة دخول/اتصال مناسبة |
| BOOT-01 | جهاز جديد online | سياق صحيح، grants المطلوبة فقط، baseline/cursors محفوظة، ثم isBootstrapped |
| BOOT-02 | تشغيل bootstrap مرتين أو بعد انقطاع | لا grants أو كيانات مكررة؛ يستأنف من checkpoint |
| MIG-01 | ترحيل مخزن قديم به outbox معلق | كل IDs وclientOperationIds والاعتماديات تبقى أو تُحجر مع سبب، ولا حذف صامت |
| MIG-02 | إعادة migration | idempotent؛ لا تضاعف عدد العمليات ولا تفقد سجلًا |
| DELTA-01 | دخول لاحق بلا تغييرات | Delta صغيرة/فارغة؛ لا full snapshot بلا سبب موثق |
| DELTA-02 | تعديل/حذف من مستخدم آخر | Delta/tombstone تعكس التغيير وتحدّث local store/query cache |
| LOGOUT-01 | Logout صريح | session/lease/cache الحساس يزول فورًا؛ تحرير قفل الجهاز bounded |
| LOGOUT-02 | Logout مع Outbox معلّق | Outbox لا يُحذف ولا يظهر لحساب آخر؛ يعرض خيار استعادة/تصدير/حذف صريح |
| CLOSE-01 | إغلاق التبويب فقط | لا signOut أو revoke أو حذف طابور |
| DATA-01 | retry لنفس العملية | نفس clientOperationId والأثر مرة واحدة |

## 10. تقسيم PRs المقترح

ترقيم PRs التالي مجرد ترتيب عمل مقترح؛ لا يُنشأ أي فرع تنفيذ قبل اجتياز بوابة المرحلة السابقة.

1. **PR-A — Auth state machine/context contract:** حالة readiness واحدة واختبارات transition/tRPC gating.
2. **PR-B — Offline boot fast-path:** local-first startup وحظر الشبكة في offline startup، مع E2E للـredirect race.
3. **PR-C — Idempotent bootstrapDeviceContext:** schema/checkpoint/grants/baseline/cursors، دون محرك sync جديد.
4. **PR-D — Local migration harness:** inventory + copy/validate/cutover + quarantine + failure injection.
5. **PR-E — Query/local Delta integration:** مجال واحد في كل مرة مع قياس payloads وtombstones.
6. **PR-F — Logout/outbox lifecycle audit:** close vs explicit logout، مسح auth/cache الحساس، حفظ/استرجاع الأعمال المعلقة بأمان.
7. **PR-G — Production E2E and performance gate:** اختبار أصلي على alias الإنتاج، إثباتات CI وdeployment/log review.

يمكن دمج PRs صغيرة إذا كانت حدود الملكية واضحة، لكن لا يدمج تغيير جلسة، ترحيل بيانات محلية، وتغيير Delta cursor في دفعة واحدة دون اختبارات مستقلة.

## 11. تعريف «صفر فقدان» ومخاطر لا يمكن إخفاؤها

- لا يمكن ضمان عدم فقدان *أي تعديل لم يُحفظ أصلًا في IndexedDB* عند انطفاء الجهاز/فشل القرص؛ لذلك يجب إظهار «تم الحفظ محليًا» فقط بعد اكتمال معاملة التخزين، لا بعد تحديث React state.
- لا يمكن التحقق من إبطال جلسة خادمية أثناء انقطاع الإنترنت. Offline access محدود زمنيًا ورخصة محلية وبيانات سبق تنزيلها؛ صلاحيات online تعاد مراجعتها عند الاتصال.
- مسح كل IndexedDB عند logout، مع وجود Outbox معلق، يتعارض منطقيًا مع Zero Data Loss. الاختيار الآمن: إخفاء/قفل بيانات المستخدم ومسح الجلسة والـcaches الحساسة، مع حفظ outbox مقيّد بالمالك حتى التسوية أو حذف مؤكد.
- كتابة الرموز يدويًا في LocalStorage لا تحسن الأمان؛ XSS يمكنه الوصول إليها. نستخدم استمرار SDK، ولا نخزن refresh token في مفتاح ثاني.
- “0ms” حرفيًا لا يتحقق مع قراءة IndexedDB غير المتزامنة؛ معيارنا عدم انتظار round-trip شبكي لعرض بيانات موجودة وقياس زمن القراءة الفعلي.
- نجاح Unit/CI لا يثبت المتصفح الحي، ونجاح deploy لا يثبت الدخول بعد restart/offline. بوابة E2E المطلوبة مستقلة.

## إصلاح سباق INITIAL_SESSION الفارغ مع قراءة الجلسة المحفوظة — 2026-10-27

6. **أول دخول مع انقطاع حقيقي:** لا توجد رخصة محلية صالحة قبل نجاح تحقق إلكتروني سابق؛ لذلك لا يجوز منح دخول offline لأول مرة اعتمادًا على إدخال كلمة المرور وحده أو اعتبار كاش حساب آخر جلسة صالحة.
7. **حالات الخطأ:** فشل قراءة جلسة SDK أو فشل الخادم يظهر كخطأ قابل للاستعادة، ولا يتحول إلى `SIGNED_OUT` صريح أو مسح للكاش أو حلقة تحويل بين `/login` و`/workspace`.

### سياسة حالة الاتصال

- فشل probe واحد لـ `/api/health` غير كافٍ لتقرير أن الجهاز offline أو أن جلسة المصادقة يجب أن تتوقف. تُبقي المنصة الحالة مجهولة مؤقتًا وتعيد الفحص سريعًا؛ لا تُعلن عدم الوصول إلى خادم PowerHub إلا بعد دورتين متتاليتين فاشلتين.

- **القبول:** اختبار تجديد جلسة قرب الانتهاء، ومشاركة الطلبات المتزامنة، والرجوع إلى رمز ما زال صالحًا عند فشل عابر، ومنع الرمز المنتهي، واستعادة حدث تجديد من تبويب آخر؛ ثم كل بوابات CI على الرأس النهائي؛ ثم اختبار متصفح مصادق يشمل login وreload وتبويبًا ثانيًا وتجديدًا حقيقيًا ثم نجاح `auth.me`. HTTP 200 أو نجاح readiness لا يثبتان الوصول إلى مساحة العمل. لا دمج أو نشر إنتاجي قبل اختبار القبول التفاعلي.


### حالة استعادة الجلسة المحفوظة عند فراغ الذاكرة — 2026-10-28

- أضيف اختبار انحدار للحالة التي يُعاد فيها `null` من قراءة الجلسة بسبب فترة تهدئة سابقة بينما بقي خطأ قراءة معروفًا. هذا الرد لا يثبت أن المستخدم سجّل الخروج.

## متابعة عاجلة — تضارب تجديد الجلسة ومؤشر الاتصال عند بدء الموقع — 2026-10-28

- **سبب تضارب التجديد:** كان PowerHub ينفذ `supabase.auth.refreshSession(session)` بتمرير نسخة الجلسة الموجودة في الذاكرة. هذا قد يتنافس مع `autoRefreshToken` أو عملية تجديد من تبويب آخر، حتى إذا كان عميل Supabase نفسه يقفل/يوحّد عملية التجديد داخل الـSDK. كما أن مسار `refreshSession(session)` لا يستخدم نفس سلوك `getSession()` الذي يعيد قراءة الجلسة الفائزة من التخزين بعد تنافس التبويبات. حين كانت النتيجة `data.session === null` بلا خطأ، كان الغلاف يترجمها إلى `PowerHubSessionRefreshFailedError`.
- **التصحيح:** أزيل التجديد اليدوي من مسار tRPC. يتشارك كل مستهلكي ترويسات التبويب Promise واحدة، ويستدعي المسار `supabase.auth.getSession()` لقراءة الجلسة الحالية مع تنسيق التجديد الداخلي للـSDK. لا تُمحى جلسة صالحة عند نتيجة null غير الحاسمة إذا لم يصل حدث مصادقة أحدث؛ أما `SIGNED_OUT` أو تبديل الحساب فيبقى authoritative. وتظل المهلة محدودة؛ إذا انتهت مهلة المستهلك قبل انتهاء عملية SDK يبقى single-flight مقفلاً حتى تستقر العملية بدل إطلاق عملية جديدة لكل طلب.
- **إصدار SDK:** القفل في `pnpm-lock.yaml` هو `@supabase/supabase-js/@supabase/auth-js 2.117.2`، ويتضمن إصلاح إرجاع الجلسة المخزنة بعد فوز تبويب آخر بتجديدها. كانت المشكلة في تجاوز ذلك المسار باستدعاء `refreshSession(session)` صراحة. مرجع التغيير: [supabase-js PR #2698](https://github.com/supabase/supabase-js/pull/2698).

- **القبول:** CI وSecurity وAdmin Guard وPostgreSQL على SHA واحد، ثم فحص المعاينة. تُغطي الاختبارات نتيجة الجلسة الفارغة مع بقاء جلسة صالحة ومشاركة عمليات الترويسات، ومنع الرمز المنتهي، وتأخير حكم offline عند بدء الموقع. يبقى تسجيل دخول مصادق فعلي، وإعادة تحميل، وتبويبان، ونجاح `auth.me` وظهور بيانات المساحة شرطًا مستقلًا قبل الدمج/الإنتاج. لا تغييرات على RLS أو مخطط/بيانات قاعدة البيانات.

## متابعة — توحيد قراءة جلسة SDK وعزل auth.me عن دفعات tRPC — 2026-10-28

- **عيب التزامن في الشفرة السابقة:** كان `getSupabaseSession()` يخزّن وعد `Promise.race([sdkRead, timeout])` ويفك القفل عند انتهاء مهلة المستدعي حتى عندما يظل طلب `supabase.auth.getSession()` الأصلي معلّقًا. وكان `resolveLatestSupabaseSessionForAccessToken()` يملك قفلًا منفصلًا ويبدأ طلب `getSession()` ثانيًا. كما أن أول قراءة قد تستهلك 5 ثوانٍ، ثم لا يبقى من المهلة الإجمالية 7.5 ثانية سوى 2.5 ثانية للمحاولة الثانية.
- **التصحيح:** أصبح هناك موضع واحد لاستدعاء SDK، مع قفل يحتفظ بوعد العملية الأصلية ومهلة مستقلة لكل مستدعٍ. انتهاء مهلة القراءة الاعتيادية لا يحرر القفل ولا يسمح بعملية SDK منافسة؛ يستعمل مسار الرمز الاحتياطي الوعد نفسه. لا يوجد استدعاء يدوي لـ`refreshSession(session)`.
- **عيب انتظار auth.me:** كان `auth.me` يستخدم `httpBatchLink` مع استعلامات بدء المساحة، ودفعة tRPC تنتظر HTTP واحدًا مشتركًا. صار `auth.me` يمر عبر `httpLink` مستقل باستخدام `splitLink`، بينما تبقى الإجراءات الأخرى ضمن `httpBatchLink`. يستخدم النقلان نفس دالة الترويسات ونفس سياسة credentials.
- **القبول:** يلزم نجاح CI والاختبارات والبناء وSecurity وAdmin Guard وPostgreSQL على الرأس ذاته، ثم اختبار دخول حقيقي وإعادة تحميل وتبويبين ونجاح `auth.me` وظهور بيانات مساحة العمل. لا تغييرات على RLS أو مخطط/بيانات قاعدة البيانات، ولا نشر إنتاجي قبل القبول.


## إصلاح تسليم جلسة تسجيل الدخول قبل التحقق الخادمي — 2026-10-28

- **السبب المباشر لرسالة بطاقة الدخول:** كانت `LoginPage` تبدأ مؤقتًا مدته 8 ثوانٍ بعد نجاح `signInWithPassword`، ولا تنتقل إلى مساحة العمل حتى يصبح `isAuthenticated` صحيحًا. هذا العلم ينتظر `auth.me` ونتيجة فحص الاتصال، بينما مهلة التحقق من الملف الشخصي 18 ثانية ومراحل الخادم لها حدود زمنية مستقلة. لذلك كانت البطاقة تعلن فشل التهيئة قبل اكتمال المسار، ثم يدخل المستخدم بين شاشة الدخول وRouteAccessGate.
- **التصحيح الأولي ثم المراجعة:** أضيف `acceptSupabaseSignInSession(session)` لتثبيت الجلسة الموثوقة الراجعة من تبادل كلمة المرور فورًا في الحالة المشتركة للعميل، وإلغاء backoff القراءة السابق، وإبلاغ AuthProvider بانتقال `SIGNED_IN` متزامن. يمنع رقم مراجعة الجلسة قراءة SDK أقدم معلقة من الكتابة فوق جلسة الدخول الجديدة. **بعد مراجعة انتقالات المسار، لم يعد التوجيه الفوري مقبولًا:** تسليم الجلسة لا يثبت نجاح `auth.me`؛ لذلك تبقى الصفحة في حالة انتظار/استرداد حتى يثبت AuthProvider `isAuthenticated`. لا يُعرض المحتوى المحمي ولا تُرسل طلبات مجال لمجرد وجود لقطة جلسة.
- **تضييق التشخيص:** أضيف logging منقح يفرق بين فشل حلّ Access Token قبل إرسال HTTP وبين فشل/تأخر استجابة `auth.me`. الحقول تقتصر على المرحلة والمدة وأسماء الأخطاء وحالة صلاحية الرمز؛ لا تسجّل JWT/refresh token أو ترويسات أو بريدًا أو معرف مستخدم.
- **اختبارات الانحدار:** اختبار جلسة مخصص يثبت أن استجابة دخول ناجحة تصبح الجلسة الحالية دون قراءة تخزين إضافية، وأن قراءة قديمة معلقة تنتهي بـ`null` لا يمكنها تجاوز جلسة الدخول الجديدة. اختبارات LoginPage وعقد `offline-auth-state` تثبت تسليم الجلسة الفوري إلى الحالة المشتركة، ومنع التوجيه اعتمادًا على `hasSupabaseSession` أو استجابة كلمة المرور وحدها، والانتقال فقط بعد تأكيد `isAuthenticated`. اجتازت بوابات CI وSecurity وAdmin Guard وPostgreSQL على SHA `64f790bec9aa7546f0b699c4ac3150264dd5cdf0` بتاريخ 2026-10-28؛ أي تعديل لاحق يعيد فتح شرط التحقق على SHA الجديد. اختبار المتصفح الحقيقي ما زال مطلوبًا قبل الدمج أو نشر الإنتاج. لا تغييرات على RLS أو مخطط/بيانات قاعدة البيانات.

## استكمال تشخيص رفض جلسة الدخول ورمز الوصول — 2026-10-28

- **رسالة المتصفح الجديدة:** `Supabase returned no usable session after sign-in.`+ تظهر من حارس التطبيق المحلي في `acceptSupabaseSignInSession` قبل أن تعتبر الجلسة مشتركة، لأن الحارس كان يخلط بين «وجود جلسة راجعة من SDK» وبين «صلاحية Access Token حاليًا وفق تلميح انتهاء محلي». وبالتزامن ظهرت `PowerHubSessionRefreshFailedError` مع السبب المحلي `Supabase session lookup completed without a usable session.`.
- **تضييق الإصلاح:** قبول الجلسة في الحالة المشتركة أصبح يتطلب هوية مستخدم ورمز وصول غير فارغين فقط. هذا لا يسمح بإرسال الرمز: `createSupabaseAccessTokenResolver` يظل مسؤولًا عن رفض الرمز المنتهي/غير القابل للتحقق، وطلبات tRPC لا تتجاوز ذلك. الهدف أن لا يُرفض تسليم جلسة SDK قبل أن يستطيع مسار الاسترداد الطبيعي فحصها.
- **تصحيح حد انتهاء الرمز:** عندما يكون Access Token JWT قابلًا للقراءة، أصبحت `exp` داخل الرمز هي المصدر الأساسي لانتهاء صلاحية bearer؛ وتُستخدم `session.expires_at` كبديل فقط عندما لا يتوفر `exp` مقروء. يغطي اختبار الانحدار حالة تزامن يكون فيها `expires_at` قديمًا بينما `exp` للرمز الحالي ما زال صالحًا، وكذلك حالة JWT منتهي مع metadata مستقبلية. هذا تحقق محلي فقط ولا يحل محل التحقق الخادمي.
- **اختبار إضافي:** تغطية استجابة دخول لها هوية ورمز لكن تلميح انتهاء قديم، مع التأكد أن اعتماد الجلسة لا يجعل الرمز المنتهي قابلًا للإرسال. يجب انتظار البوابات الأربع على SHA الذي يتضمن هذا التغيير.
- **حد إثبات مهم:** لم تصلنا قيمة `tokenExpirySource` و`tokenExpiresAt` و`tokenUsable` الكاملة من سجلات المتصفح المبلغ عنها، ولم يجر اختبار متصفح تفاعلي بحساب staging معزول. لذلك يبقى ما إذا كان سبب الحالة الفعلية metadata قديمة، أو رمزًا منتهيًا فعليًا/رفض refresh token، مفتوحًا حتى فحص التشخيص الآمن بعد هذا الإصلاح. لا نضيف عميل Supabase ثانيًا، ولا تدوير refresh يدويًا متوازيًا، ولا نحذف الجلسة أو IndexedDB أو Outbox.

| `FORBIDDEN` بسبب قفل جهاز معروف | تمييز «الحساب مستخدم على جهاز آخر» وإرشاد المستخدم إلى الجهاز السابق؛ أي نقل إلى جهاز جديد يجب أن يكون إجراءً صريحًا لا takeover صامتًا | لا تصف كل `FORBIDDEN` بأنه قفل جهاز ولا تلغِ القفل تلقائيًا |
| `FORBIDDEN` بسبب دور/فرع/عملية | رسالة صلاحيات عامة آمنة تطلب مراجعة الدور أو نطاق الفرع | لا تعرض رسالة قفل جهاز بلا دليل ولا تكشف تفاصيل حساسة |
| تعذر التحقق من معرّف الجهاز | رسالة مستقلة عن قفل جهاز آخر، مع إعادة محاولة وفحص تشغيلي | لا تعِد إنشاء هوية الجهاز في كل تحميل ولا ترسل طلبًا محميًا بلا Device ID |
| لا يوجد اتصال مع رخصة offline صالحة وبيانات محلية لنفس المستخدم | فتح محلي واضح مع تمييز آخر مزامنة والعمليات المنتظرة | لا ترسل tRPC محميًا بلا Access Token ولا تدّعِ أن الخادم تحقق الآن |
| عودة الاتصال | تحقق خادمي أولًا، ثم Delta/Outbox مع عرض التقدم والتعارضات | لا تعِد تنزيل كل القوائم بلا سبب ولا تكرر أثر عملية مالية |
| تبديل الحساب | فصل بيانات العرض/الكاش حسب الهوية والنطاق، وحفظ Outbox القديم معزولًا لصاحبه | لا تعرض بيانات المستخدم السابق ولا ترسل عملياته بحساب المستخدم الجديد |
| تسجيل الخروج الصريح | إنهاء الجلسة وإبطال رخصة offline وكاش العرض الحساس؛ توضيح أن العمل غير المتزامن سيبقى معزولًا | لا تحذف Outbox أو المسودات التشغيلية بصمت |

### معيار القبول لهذه الرسائل

- تصنيف قفل الجهاز لا يعتمد على رمز `FORBIDDEN` وحده؛ يلزم سبب خادمي معروف من رسائل عقد الجهاز. أي رفض آخر يبقى رفض صلاحيات عامًّا.
- لا تُعرض رسالة الخادم الخام أو التوكن أو تفاصيل الجلسة؛ تُحوّل إلى نص آمن ومحدد الخطوة التالية.
- لكل مرحلة فشل إجراء استعادة واحد واضح على الأقل، مع انتهاء spinner ضمن مهلة، ولا ينتج عن الضغط المتكرر عاصفة refresh أو توجيه متكرر.
- تبقى معاينة PR غير معزولة عن مشروع Supabase الإنتاج خارج اختبارات تنافس الأجهزة؛ اختبارات takeover/قفل الجهاز تتطلب حسابًا وبيئة staging معزولين.
- هذه التوثيقات والاختبارات لا تعني أن E2E حي اجتاز؛ تبقى بوابة المتصفح مطلوبة قبل الدمج.


## تدقيق تصنيف خطأ الجهاز بعد تغليف tRPC — 2026-10-28

- كشف التدقيق أن بعض أخطاء tRPC قد تحمل `FORBIDDEN` في الغلاف الخارجي، بينما يكون سبب قفل الجهاز في `cause` متداخل. لا يجوز أن يعتمد التشخيص على أول كائن يحوي `data.code` فقط.
- أضيف بحث محدود الحلقة في سلسلة `cause` عن الرسائل الخادمية المعروفة الخاصة بقفل الجهاز/هوية الجهاز، من دون عرض الرسائل الخام أو التفاصيل الحساسة. يبقى `FORBIDDEN` وحده رفض صلاحية عامًّا.
- أضيف اختبار يلف رسالة قفل الجهاز داخل خطأ tRPC اصطناعي ويتأكد من تصنيفها دون كشف النص الخام؛ تعاد جميع البوابات على الالتزام الجديد قبل الدمج.


## اختبار خطأ قفل الجهاز بعد تغليف RPC — 2026-10-28

- أضيفت حالة انحدار حيث يحمل خطأ tRPC الخارجي `FORBIDDEN` ورسالة عامة، بينما تحمل `cause` المتداخلة سبب قفل الجهاز. الهدف منع الخلط بين صلاحية الحساب وقفل الجهاز عبر أغلفة النقل.
- لا تتغير سياسة قفل الجهاز ولا تخفيف أذونات الخادم؛ التحسين يخص شرح الحالة فقط. يبقى E2E الفعلي لعزل الحسابات/الأجهزة متطلبًا مفتوحًا.


## ملاحظة تشخيصية حاسمة: الخلل خاص بلابتوب واحد — 2026-10-28

- **الملاحظة التشغيلية من المستخدم:** المعاينة والإنتاج يعملان على الهاتف وعلى لابتوب آخر، بينما يظهر الخلل على اللابتوب الذي استُخدم طوال تطوير المشروع. هذا يغيّر ترتيب التحقيق: يبدأ بمقارنة حالة المتصفح/الملف المحلي على الجهاز المتعطل، ولا يثبت وحده أن السبب من المتصفح أو من الخادم.
- **قرائن الكود:** تحفظ هوية الجهاز داخل `localStorage` مع مخزن IndexedDB احتياطي؛ جلسة Supabase المستمرة يملكها SDK؛ وعامل الخدمة يملك cache منفصلًا لصفحة shell والأصول. هذه الحالات تختلف باختلاف أصل الموقع وملف المتصفح، وقد تبقى بعد `Ctrl+F5`.
- **حد مهم في تفسير السجلات:** ظهور `stage: "access-token-resolution"` يعني أن ترويسة Access Token لم تجهز وأن طلب tRPC المحمي لم يُرسل؛ لا يجوز تفسير هذه الحالة على أنها رفض لقفل الجهاز. إذا وصل الطلب ثم عاد `FORBIDDEN` فهذه مرحلة أخرى يجب تشخيصها منفصلة.
- **إجراء منع فقد البيانات:** لا تمسح Site Data أو IndexedDB أو `powerhub:device-id`، ولا تسجل الخروج لمجرد التشخيص. قد توجد عمليات Outbox محلية، وتغيير هوية الجهاز قد يجعل الخادم يعتبره جهازًا جديدًا.
- **أداة تشخيص مقيدة:** أضيف زر اختياري في شاشة الدخول لنسخ تقرير مقارنة لا يحتوي على الرموز أو البريد أو معرف المستخدم/الجهاز أو صفوف الكاش والطابور. يشمل الأصل ونوع صفحة البناء، حالة تخزين المتصفح ووجود مفتاح جلسة Supabase (عدد فقط)، وجود قواعد IndexedDB المعروفة، عامل الخدمة النشط/المنتظر، قابلية الوصول إلى `/api/health`، وحالة جلسة منقحة.
- **اختبار المقارنة:** يلزم جمع التقرير من اللابتوب المتعطل ومن جهاز يعمل، لنفس الأصل في كل مقارنة (Production مع Production، وPreview مع Preview). اختلاف الأصل متوقع أن يغيّر التخزين المحلي ومعرف الجهاز، لذلك لا تفسر تقرير Production مقابل Preview كأنهما ملف متصفح واحد.
- هذه الأداة تشخيصية فقط، ولا تغير الجلسة أو قفل الجهاز أو المخازن التشغيلية. لا يثبت نجاح زر النسخ حل المصادقة؛ يظل المطلوب تحديد المرحلة التي تختلف على اللابتوب المتعطل ثم إصلاح السبب المثبت.


## تشخيص اختلاف اللابتوب وضمان تشغيل اختبار شاشة الدخول في CI — 2026-10-28

- أفاد المستخدم أن المنصة تعمل على الهاتف ولابتوب آخر، بينما تختلف النتيجة على لابتوبه المعتاد. لا يثبت ذلك وحده سببًا محليًا، لكنه يرفع أولوية مقارنة حالة التخزين وملف المتصفح وService Worker ومرحلة استخراج Access Token.
- أضيفت شاشة الدخول خيارًا يدويًا لتجميع تقرير آمن منقح، يجمع أصل الموقع ومعرّف ملف البناء، قدرات التخزين ووجود مفاتيح الجلسة (عدد فقط)، حالة مخازن IndexedDB المعروفة، حالة Service Worker، نتيجة فحص `/api/health`، وحقول جلسة منقحة. لا يقرأ التوكن أو محتويات الجلسة/الكاش/Outbox ولا يسجل البريد أو معرّف المستخدم/الجهاز.
- **فجوة الاختبار التي اكتشفتها المراجعة:** كان `scripts/run-tests.mjs` لا يشغّل `client/src/pages/LoginPage.ui.test.tsx` صراحةً؛ لذلك وجود اختبار زر التشخيص لم يكن يضمن تنفيذه على CI. أضيف الملف إلى حلقة اختبارات الصفحات المنفصلة باستخدام `vitest.pages.config.ts` حتى يفشل CI إن تراجع سلوك شاشة الدخول أو اختبار التقرير.
- على CI أن يمر TypeScript والاختبارات وبناء الإنتاج وجميع البوابات الأربع على الرأس نفسه. هذا التغيير لا يثبت إصلاح مصادقة اللابتوب، ولا يجيز حذف بيانات المتصفح، ولا يغير RLS أو مخطط قاعدة البيانات أو قفل الأجهزة.

## مراجعة السبب الجذري وتقليل إعادة محاولات المصادقة — 2026-10-28

- **السبب الذي تأكد من المستخدم:** ساعة أحد الأجهزة كانت متقدمة بنحو 120 دقيقة؛ لذلك ظهر Access Token كأنه منتهي منذ قرابة ساعتين، وبعد تصحيح الساعة نجح الدخول. هذا يفسر الحادثة الأخيرة مباشرة، ولا يثبت أن كل الأعطال السابقة كانت من السبب نفسه.
- **قرار المراجعة:** لا نضيف تجديدًا يدويًا أو نمسح الجلسة/الكاش/معرّف الجهاز بسبب هذه الحادثة. يبقى Supabase SDK مالك دورة تجديد refresh token، ويظل Access Token المنتهي ممنوعًا من إرسال طلب محمي.
- **تعديل محدد في PR #359:** أوقفت سياسة إعادة المحاولة التلقائية لـ `auth.me` عندما يكون الخطأ معروفًا بأنه صادر قبل/أثناء تجهيز رمز الجلسة أو هوية الجهاز أو من تهدئة Supabase. إعادة `auth.me` لا تصلح ساعة النظام ولا هوية جهاز غير قابلة للقراءة؛ كانت تعيد المسار نفسه وتؤخر عرض حالة الاسترداد. بقيت إعادة المحاولة المحدودة لأخطاء النقل العامة و`GATEWAY_TIMEOUT`، وبقيت إعادة المحاولة الصريحة من المستخدم.
- **اختبار انحدار:** يثبت أن فشل token bootstrap أو هوية الجهاز لا يعاد تلقائيًا، بينما يبقى خطأ الشبكة العام قابلًا لإعادة المحاولة، ويظل `FORBIDDEN` غير قابل لإعادة المحاولة.
- **حدود القرار:** لم تُلغَ حدود المهلة، أو حماية منع إرسال رمز منتهي، أو منع عاصفة refresh، أو عزل الحساب/الجهاز. المهلات لا تؤخر المسار الناجح بذاتها؛ وهي تحكم زمن التعافي عند التعليق. يجب قياس زمن الدخول الفعلي على المتصفح قبل تقليصها، لا تخفيضها عشوائيًا.
- **التحقق المطلوب:** إعادة جميع البوابات على رأس PR الجديد نفسه، ثم اختبار متصفح حقيقي على جهاز بساعة صحيحة يشمل الدخول الأول، reload، تبويبين، وانقطاع/عودة الاتصال. لا دمج أو نشر إنتاجي قبل ذلك.

## مرحلة لاحقة مقترحة: نقل جلسة الجهاز بإقرار صريح مع حماية Outbox — 2026-10-28

هذه المرحلة مستقلة عن تقليل زمن الدخول في PR #359؛ لا تُدمج معها في نفس التغيير، ولا تبدأ قبل إكمال بوابات PR الحالي واختبار المتصفح الأساسي. الهدف تمكين صاحب الحساب من نقل الجلسة من الجهاز (أ) إلى الجهاز (ب) بإجراء مقصود، دون تسجيل خروج شامل غير مقصود أو فقد العمليات المحلية.

### السلوك المطلوب

1. **مطالبة عادية بالجهاز:** إذا لم يوجد قفل سابق، أو حرره الجهاز المالك صراحةً، يستطيع الجهاز (ب) امتلاك القفل. إذا كان القفل لنفس الجهاز، يُجدد كالمعتاد.
2. **جهاز مختلف موجود:** لا تستبدل هوية الجهاز لمجرد أن القفل قديم أو انتهت مدة الـ lease. يعيد الخادم نتيجة تعارض محددة وآمنة، وتعرض الواجهة: «هذا الحساب يعمل أو كان مسجلًا على جهاز آخر. نقل الجلسة إلى هذا الجهاز قد يوقف مزامنة العمليات المعلّقة على الجهاز السابق. هل تريد المتابعة؟» مع خيارين واضحين: «إبقاء الجهاز السابق» و«إنهاء الجلسة القديمة والبدء هنا». يمكن عرض آخر نشاط معروف، لكن لا نكشف معرّف الجهاز الداخلي.
3. **تأكيد النقل:** لا ينفذ النقل عند مجرد فتح صفحة الدخول أو عند ظهور رسالة التعارض. يتطلب إجراء تأكيد صريحًا بعد مصادقة حديثة، ويأخذ الخادم هوية المستخدم من الجلسة الموثقة لا من مدخل يرسله العميل.
4. **تغيير الملكية:** ينفذ RPC خادمي محمي بمعاملة وقفل تنافسي للمستخدم؛ يعيد فحص المالك الحالي داخل المعاملة، ثم ينقل ملكية القفل إلى الجهاز (ب) ويزيد رقم جيل/إصدار جلسة الجهاز أو يحدّث ما يعادله، ويكتب سجل تدقيق لنتيجة النقل. يجب أن تكون العملية متكررة بأمان (idempotent) حتى لا ينفذ الضغط المكرر أو انقطاع الاستجابة عمليات متعارضة.
5. **منع الجهاز السابق:** يُرفض أي طلب محمي أو مزامنة من الجهاز (أ) بعد النقل. لا يكفي أن يُرفض `auth.me` فقط: يجب تدقيق كل مسارات tRPC وREST وDelta/Outbox والعمليات الحساسة والتأكد من أن التحقق من ملكية الجهاز نافذ على كل مسار. كما يجب معالجة سباق الطلبات التي بدأت قبل النقل؛ التحقق في middleware ثم تنفيذ كتابة منفصلة قد يترك نافذة سباق، لذا يلزم fence/version check عند حد الكتابة أو داخل المعاملة للعمليات المالية والكتابات الحساسة.
6. **الرموز لدى Supabase:** لا يُفترض أن تحديث قفل PowerHub يبطل تلقائيًا Access Token موجودًا. توثيق Supabase يوضح أن Access JWT الذي أُصدِر بالفعل قد يبقى صالحًا حتى انتهاء `exp` حتى بعد إبطال جلسة/Refresh Token. كذلك `signOut({ scope: 'others' })` يؤثر في جلسات أخرى للحساب عمومًا، وليس «رمز الجهاز القديم وحده»؛ لا يُستدعَ إلا بعد تقييم تأثيره على كل الجلسات الأخرى واختباره في بيئة معزولة. يبقى قفل PowerHub فاصلًا لازمًا للرفض الفوري على مسارات الخادم. المصدر: https://supabase.com/docs/reference/javascript/auth-signout وhttps://supabase.com/docs/guides/auth/sessions.
7. **الجهاز القديم غير المتصل:** لا يمكن إيقاف واجهته أو مسحه عن بعد وهو بلا اتصال. يُسمح بالعمل المحلي ضمن سياسة Offline الحالية، لكن عند عودة الاتصال يجب إيقاف Sync Push قبل إرسال أي عملية إذا لم يعد الجهاز مالك القفل/الإصدار. تُحفظ عملياته في Outbox معزولة لصاحبها وتظهر له حالة «الجهاز لم يعد مخولًا للمزامنة» وخيار تسوية/تصدير/استعادة القفل عبر إجراء مخول؛ لا تُحذف ولا يعاد إرسالها بهوية الجهاز أو حساب آخر تلقائيًا.
8. **عدم إضافة مصدر ملكية مكرر:** الجدول الحالي `public.powerhub_user_device_locks` يملك `device_id`، بينما `active_device_id` هو اسم عمود في نتيجة `powerhub_claim_user_device` وليس حقلًا مستقلًا في الجدول. يجب البناء على هذا المصدر الوحيد وتحديد الحاجة الفعلية إلى عمود جيل/حالة تدقيق، لا إضافة `active_device_id` مكررًا.
9. **مراجعة الاسترداد القديم:** دالة `powerhub_claim_user_device` الحالية تستطيع الاستيلاء على قفل جهاز آخر بعد 15 دقيقة من عدم النشاط، أو عند انتهاء lease. يجب مراجعة هذا السلوك مع ميزة Takeover حتى لا يحدث نقل ضمني رغم أن الجهاز القديم قد يحمل عمليات Offline معلقة. تكون السياسة صريحة وقابلة للاسترداد، ولا تُستنتج سلامة Outbox من قيمة `last_seen_at` وحدها.

### اختبارات قبول إلزامية

- جهاز (ب) يحصل على تعارض صريح، ولا تتغير ملكية القفل قبل التأكيد.
- تأكيد صحيح ينقل الملكية مرة واحدة، والطلب المكرر آمن، والطلبان المتزامنان لا يملكان الجهاز في الوقت نفسه.
- الجهاز (أ) يُرفض في `auth.me` وجميع مسارات المجال والمزامنة بعد النقل، وتُختبر العمليات التي بدأت بالتوازي مع النقل.
- فشل إبطال جلسة Supabase أو انقطاع الشبكة في منتصف الإجراء لا يترك واجهة تدعي نجاحًا غير صحيح؛ تسجل حالة الخطوة وتتيح استردادًا آمنًا.
- أثناء Offline، تبقى بيانات الجهاز (أ) وOutbox محفوظة؛ وبعد الاتصال لا تُرسل أي عملية قبل فحص ملكية الجهاز، ولا تُرسل العمليات المرفوضة تحت حساب أو جهاز آخر.
- تُختبر الحالات على staging وحسابي اختبار مخصصين، مع تزامن طلبات وتبويبات متعددة. لا تُجرّب takeover على حساب أو قفل إنتاجي.
- تُراجع التغييرات والـ migrations وACL/RLS والـ audit log مع اختبارات PostgreSQL والأمان، ثم E2E حقيقي على build واحد؛ لا يكفي نجاح CI وحده.

**حدود التنفيذ:** هذا توثيق مواصفات للمرحلة التالية فقط، وليس إعلانًا بأن Takeover مطبق. لا تغييرات في قاعدة البيانات أو قفل الجهاز أو استدعاءات Supabase Admin ضمن PR #359 نتيجة هذا التوثيق.

## تشخيص انحراف ساعة الجهاز عن وقت الخادم — 2026-10-28

- **الحادثة المثبتة:** أظهر تقرير المتصفح جلسة ورمزًا موجودين، لكن صلاحية الرمز المتبقية كانت نحو `-120` دقيقة. بعد تصحيح ساعة الجهاز نجح الدخول. يثبت ذلك سبب الحادثة الأخيرة فقط، ولا يثبت أن كل أعطال المصادقة السابقة لها السبب نفسه.
- **الإجراء الوقائي:** يسجل فحص `/api/health` فرقًا تقريبيًا بين ساعة الجهاز وترويسة `Date` من رد PowerHub، باستخدام منتصف زمن الطلب لتقليل أثر تأخر الشبكة. الانحراف الأكبر من خمس دقائق يصنف كساعة غير متزامنة.
- **حدود الأمان:** القياس للتشخيص ومنع تكرار طلبات التطبيق المحمية فقط. لا يُمدّد `exp` ولا يقبل JWT منتهيًا ولا ينشئ جلسة، ولا يغير قفل الجهاز أو RLS. يبقى تحقق الخادم هو المرجع. إذا لم تتوفر ترويسة `Date`، فالحالة غير معروفة ولا يفترض العميل أن الساعة صحيحة.
- **السلوك المتوقع:** عند اكتشاف انحراف كبير، يتوقف مسار ترويسة API قبل حل الرمز، وتُمنع إعادة المحاولة التلقائية لـ`auth.me`، وتظهر رسالة تطلب ضبط التاريخ والوقت والمنطقة الزمنية ثم إعادة التحميل والمحاولة. لا يحدث تسجيل خروج تلقائي ولا مسح للكاش أو Outbox.
- **القبول:** اختبارات تقدير الانحراف وحد الخمس دقائق وترويسة وقت الخادم ورسالة خطأ آمنة وعدم إعادة المحاولة؛ ثم نجاح جميع البوابات على الرأس النهائي واختبار دخول حقيقي. لا يُدمج PR بناءً على CI وحده.

## تنفيذ أول شريحة من منسق تهيئة الجهاز — 2026-10-28

- أضيف `bootstrapDeviceContext` كمنسق قابل للاستئناف يعتمد مفتاحًا مكوّنًا من `userId + tenantId + siteId + deviceId + localSchemaVersion + bootstrapVersion`، مع تخزين نقطة الحالة في `bootstrapState` ضمن قاعدة `powerhub-offline-workspace` (الإصدار 5). ترقية المخطط تضيف مخزنًا جديدًا فقط ولا تحذف المخازن السابقة.
- يبدأ التنفيذ في مكوّن خلفي بعد نجاح `auth.me` دون إدخاله في بوابة الدخول أو منع عرض الواجهة. على الجهاز الذي اكتملت تهيئته، تؤدي إعادة الفتح إلى قراءة علامة النطاق ومؤشرات Delta المحلية فقط ثم الخروج سريعًا.
- في التهيئة الناقصة، يُحل النطاق مجددًا من `sites.list` و`staff.myAccess` الخادميين؛ تُطلب نطاقات الأرقام فقط عند توافر صلاحيات `manageSubscribers` و`issueInvoices`، ويُحفظ `requestId` قبل تنفيذ الحجز ثم يُعاد استعماله عند الاستئناف.
- يحفظ أول snapshot القوائم المتوافقة مع Delta (المواقع والمشتركون والمولدات والتعرفة بحسب الدور) باستخدام `persistOfflineQueryForDeltaSync`. لا تُثبت `isBootstrapped` حتى تكون مؤشرات Delta المحلية للمجالات المطلوبة موجودة؛ مصدر هذه المؤشرات هو `OfflineDeltaSyncRuntime` القائم وليس محركًا جديدًا.
- اختبارات الخدمة تغطي إعادة الاستئناف بعد نتيجة شبكة ملتبسة، ثبات `requestId`، عدم تكرار الحجز/اللقطة، وعدم تعيين `isBootstrapped` قبل اكتمال مؤشرات Delta، وعزل المستخدم/الفرع/الجهاز/إصدار المخطط.
- **غير مغلق بعد:** يجب أن تنجح بوابات CI على الرأس النهائي، ويُختبر المتصفح فعليًا مع حساب staging مخصص: أول دخول، انقطاع في منتصف التهيئة، reload، دخول متكرر لا يسحب لقطة كاملة، ثم reconnect/Delta. لا يعني إنشاء نقطة الحفظ وحده أن كل مجال بيانات مخزن محليًا بالكامل.
