# خطة PowerHub لمصادقة مستدامة وتهيئة الجهاز الأول (First-Login Bootstrap)

- **الحالة:** خطة تنفيذ موثقة على `main`؛ لا تعني أن جميع المراحل منفذة أو أن الدخول دون اتصال اجتاز اختبار متصفح حي.
- **تاريخ التوثيق:** 2026-10-26
- **تحديث الحالة:** أكد المشغّل أن مشكلة الدخول وحلقة التوجيه حُلّت في الاستخدام الفعلي. هذا لا يغلق اختبارات إعادة فتح المتصفح أو العمل دون اتصال أو Delta أو مراقبة refresh.
- **PR التنفيذ الموحد:** `feat/auth-local-first-single-pr` يجمع تغييرات بدء Local-First، وتهيئة الكاش، وبوابات المصادقة، والاختبارات الرجعية في PR واحد. تبقى المراحل مفتوحة حتى اجتياز بواباتها.
- **نقطة الأساس:** `a2612a00843a51826ec5e64e70029aada1d35371` (دمج PR #357).
- **صلة الخطة:** [خطة Local-First + Delta Sync الرئيسية](../p7-offline-first-delta-sync-roadmap.md).
- **هدف المستخدم:** فتح مساحة العمل بسرعة من جلسة محفوظة، إظهار آخر البيانات المحلية المسموح بها، منع حلقات التوجيه وطلبات المصادقة المتكررة، تهيئة الجهاز الأول مرة واحدة، والحفاظ على كل عملية غير متزامنة إلى أن تُسوّى أو يطلب المستخدم حذفها صراحةً.

## 1. الملخص التنفيذي والقرارات المعمارية

تُنفَّذ الخطة على مراحل صغيرة، مع بوابة اختبار وقياس لكل مرحلة. المصدر النهائي للهوية والصلاحية وبيانات العمل هو Supabase/PostgreSQL والخادم؛ البيانات المحلية نسخة عرض/عمل محلية مقيدة وليست بديلًا عن التحقق الخادمي أو قفل الجهاز أو RLS.

### قرارات ملزمة

1. **عميل مصادقة واحد:** يبقى عميل Supabase في `client/src/lib/supabase.ts` هو العميل المشترك. يظل SDK مالك دورة تجديد الرموز الطبيعية؛ لا نعيد إدخال استدعاءات `refreshSession()` اليدوية أو تدوير refresh token من عدة مسارات.
2. **لا رموز مكررة في مخازن مخصصة:** يستخدم التطبيق استمرار جلسة Supabase الذي يملكه SDK (`persistSession: true`). لا ينسخ access token أو refresh token إلى مفاتيح LocalStorage خاصة بـPowerHub. يمكن حفظ *ملخص سياق غير سري* وبيانات الكاش، لكن لا يصبح هذا الملخص إثبات صلاحية.
3. **لا قاعدة عمل محلية موازية:** خط الأساس يستخدم IndexedDB أصليًا، لا Dexie.js. قاعدة `powerhub-offline-workspace` هي مخزن العمل التشغيلي المشترك (الإصدار 4)، بينما الكاش والمصادقة في مخازن منفصلة. **لا نضيف Dexie ولا ننقل الجداول إليه ضمن هذه الخطة تلقائيًا**؛ إضافة طبقة ثانية الآن ترفع خطر ازدواج الطوابير وفقد العمليات. إذا كان اعتماد Dexie شرطًا غير قابل للتغيير، يُفتح ADR مستقل أولًا مع خطة ترحيل قابلة للعكس.
4. **عرض محلي سريع، لا تجاوز للمصادقة:** يمكن إظهار snapshot محلي بسرعة عند وجود جلسة/رخصة offline صالحة وكاش لنفس الحساب والنطاق. لا يجوز استخدام الكاش لتمرير طلب tRPC محمي دون Access Token صالح أو لمنح دور/مستأجر/فرع غير متحقق منه.
5. **لا تعهد حرفي بـ0ms:** IndexedDB غير متزامن ويحتاج قراءة فعلية؛ الوعد القابل للقياس هو عرض آخر snapshot فور اكتمال القراءة المحلية، من دون انتظار الشبكة. يقاس الزمن بدل ادعاء زمن صفري حرفيًا.
6. **الحفاظ على العمل يتقدم على التنظيف الصامت:** لا يجوز حذف Outbox أو المسودات غير المزامنة عند تسجيل الخروج لمجرد أنها «بيانات تشغيل». يسحب الخروج الجلسة ويمنع عرض بيانات الحساب؛ تبقى العمليات المعلقة معزولة ومقفلة على هوية صاحبها حتى يعاود تسجيل الدخول أو يزامنها/يصدّرها/يؤكد حذفها صراحةً. حذفها تلقائيًا يتناقض مع شرط Zero Data Loss.
7. **لا تهيئة شبكة جديدة تنافس Delta Sync:** `bootstrapDeviceContext` سيكون منسقًا idempotent فوق APIs والتخزين ومحرك Delta/Outbox الموجودين، لا محرك مزامنة ثانٍ ولا نسخًا مستقلة من قواعد الأعمال.

## 2. خط الأساس الفعلي في المستودع

| المجال | الوضع المثبت في الكود | النتيجة المطلوبة |
|---|---|---|
| جلسة Supabase | `client/src/lib/supabase.ts` ينشئ عميلًا واحدًا باستخدام `persistSession` و`autoRefreshToken` و`detectSessionInUrl`؛ توجد قراءة جلسة محدودة المهلة ومسار تشخيص/تهدئة | مالك واحد لدورة الجلسة، قراءة مشتركة محدودة، وتعافٍ بلا سباقات/عواصف refresh |
| ترويسات tRPC | `client/src/main.tsx` يحصل على Access Token ومعرّف الجهاز قبل الطلبات المحمية ويضبط Authorization و`x-powerhub-device-id` | توحيد readiness contract لمنع استعلامات المجال قبل حل الجلسة ومعرّف الجهاز والسياق التنظيمي |
| سياق الواجهة | `AuthProvider/useAuth` موجود، ويكشف المستخدم وحالة الجلسة/المصادقة والتحميل والخطأ؛ سياق المستأجر/الفرع وbootstrap readiness ليسا عقدًا مركزيًا مكتملًا | إضافة `tenantId/siteId/deviceId/isBootstrapped/bootState` كمخرجات واضحة ذات مصدر موثوق |
| مصادقة Offline | `client/src/lib/offline-auth.ts` يحتفظ برخصة محلية موقعة بـHMAC، مرتبطة بمعرّف المستخدم، مدتها الحالية 48 ساعة، ومفتاحها في IndexedDB | حفظ سلوك واضح: الرخصة تتيح UI/القراءة المحلية ضمن المدة، لا API online أو صلاحيات خادمية |
| كاش الاستعلام | `client/src/lib/offline-query-cache.ts` يستخدم `powerhub-offline-cache` الإصدار 2، منفصلًا عن Auth/Outbox، مع allowlist وحدود عدد/حجم | توحيد سياسة الكاش ووضوح نطاق المستخدم/المستأجر/الفرع وحداثة البيانات والتنظيف |
| مساحة العمل والطوابير | `client/src/lib/offline-workspace-db.ts` يعرّف `powerhub-offline-workspace` الإصدار 4 ومخازن العمليات والنطاقات والمطالبات والقراءات والمؤشرات والكيانات والتعارضات والـmetadata | حفظ المخطط كقاعدة تشغيل واحدة وترحيل مخازن الإصدارات السابقة دون إسقاط المصدر قبل التحقق |
| Delta / Outbox | موجودان في `client/src/lib/offline-delta-sync.ts` و`client/src/lib/offline-work-queue.ts` وملفات metadata/range الحالية؛ التغطية تختلف باختلاف المجال | bootstrap الأول يسجل baseline/cursors، ثم يتنحى ويترك التغييرات اللاحقة للمحرك نفسه |
| التهيئة | `bootstrapOfflineState()` في `client/src/main.tsx` يهيئ كاش المستخدم بصورة غير متزامنة؛ لا توجد دالة عامة باسم `bootstrapDeviceContext` | بناء منسق جديد، محدود المسؤولية، وقابل للاستئناف والتحقق، لا استبدال bootstrap الموجود عشوائيًا |
| تخصيص الأرقام | واجهة `powerhub.offlineNumbering.reserve` والعميل `offline-number-ranges` موجودان؛ الحجوزات مرتبطة بالمستخدم والمستأجر والفرع والجهاز ونوع الرقم/القسم | إعادة استعمال الحجز الموجود بمفتاح طلب ثابت وبحسب الدور، دون إنشاء allocator ثانٍ |
| UI/التوجيه | `RouteAccessGate` و`LoginPage` يعالجان التعافي والعودة إلى المساحة؛ PR #356 و#357 عالجا استعادة جلسة محفوظة وسباق أول probe | إغلاق حلقات التوجيه من خلال state machine واختبارات متصفح على نفس origin بعد النشر |

## 3. عقد الحالة المركزي (Auth + Device Context)

ينشأ عقد TypeScript واحد، من خلال `AuthProvider/useAuth` أو وحدة سياق مشتركة مستخدمة داخله، ويكون على الأقل:

```ts
type BootState =
  | "initializing"
  | "restoring-local"
  | "validating-online-session"
  | "resolving-organization"
  | "bootstrapping-device"
  | "ready"
  | "offline-ready"
  | "needs-login"
  | "recoverable-error";

type AuthDeviceContext = {
  user: AuthenticatedPowerHubUser | null;
  tenantId: number | null;
  siteId: number | null;
  deviceId: string | null;
  isAuthenticated: boolean;
  isBootstrapped: boolean;
  isLoading: boolean;
  bootState: BootState;
  isOnline: boolean;
  lastSyncedAt: string | null;
  refresh(): Promise<void>;
  logout(): Promise<void>;
};
```

هذا العقد توضيحي؛ أنواع المستخدم/الموقع يجب أن تطابق أنواع المشروع الفعلية ولا تُنسخ الأنواع بشكل يدوي متضارب.

### قواعد جاهزية الطلبات

- يُسمح بالاستعلامات العامة واللازمة لإكمال المصادقة والتهيئة فقط قبل اكتمال السياق.
- لا تبدأ استعلامات بيانات مجال محمية قبل وجود جلسة online قابلة للاستخدام أو حالة `offline-ready` بكاش صالح، وحل `deviceId`، وحل `tenantId/siteId` المسموح بهما.
- **حالة offline لا تعني أن tRPC authenticated.** عند غياب Access Token صالح، لا ترسل أي طلب محمي؛ استخدم القراءة المحلية والطابور فقط.
- كل طلب محمي online يحمل `Authorization: Bearer <access_token>` و`x-powerhub-device-id`. لا يعتبر `tenantId/siteId` القادم من المتصفح مصدر صلاحية؛ يعيد الخادم حل الصلاحيات ونطاق الفرع ويتحقق من قفل الجهاز.
- لا يعاد استخدام Query Cache أو cursor أو grants عند تبديل user/tenant/site/device؛ كل مفتاح محلي وكل سجل تشغيل يقيّد على الهوية والنطاق الكاملين.
- الأخطاء العابرة تُعرض بوصفها تعافيًا قابلًا لإعادة المحاولة، ولا تحول إلى تسجيل خروج ضمني. الرفض الصريح/إبطال الصلاحية يبقى قرارًا مختلفًا.
- لا يوجد redirect إلى `/login` طالما أن state machine في مرحلة استعادة محلية/تحقق محدود أو يوجد خطأ قابل للتعافي؛ تنتهي كل مرحلة بحد زمني وحالة مرئية.

## 4. دورة الجلسة المستدامة

### عند التشغيل أو إعادة فتح المتصفح

1. اقرأ الحالة المحلية والرخصة وملخص المستخدم/النطاق من مخازنها الحالية، بقراءات محدودة المهلة.
2. إذا كان المتصفح يبلغ صراحةً أنه offline، وكانت الرخصة صحيحة وغير منتهية، والملف الشخصي والـsnapshot يعودان لنفس المستخدم والنطاق، فاعرض `offline-ready` من دون طلبات شبكة عند الإقلاع. يجب ألا تستدعي تهيئة هذا المسار `auth.me` أو tRPC محميًا.
3. إذا كان الاتصال محتملًا، ابدأ فحص الاتصال والمصادقة بصورة غير حاجبة لعرض shell المحلي. ينتظر حارس التوجيه نتيجة أول probe فقط عندما يكون هناك snapshot ورخصة Offline صالحة؛ لا يعلّق المستخدم العادي ولا يبدأ حلقة redirect.
4. عند وجود جلسة Supabase صالحة، تحقق من `auth.me` ومن سياق المستخدم/المستأجر/الموقع/الجهاز قبل عرض واجهة online المصادق عليها.
5. عند تعذر الشبكة مؤقتًا، احتفظ بالـsnapshot المحلي والرخصة الصالحة واعرض حالة Offline/آخر مزامنة؛ لا تعتبر ذلك نجاحًا جديدًا لمصادقة الخادم.
6. عند انتهاء الرخصة أو فقدان المفتاح/تلف السجل، لا يتجاوز التطبيق بوابة المصادقة ولا يستنتج هوية المستخدم من مفتاح LocalStorage قابل للتعديل؛ يعرض شاشة دخول/استعادة واضحة.

### عند عودة الشبكة

- يستخدم SDK دورة التجديد الطبيعية؛ لا توجد مهمة refresh مستقلة لكل صفحة أو tab.
- عند تأكيد `TOKEN_REFRESHED`، ترفع حالة readiness وتعيد محاولة الاستعلامات النشطة التي فشلت بسبب غياب token، مع قفل/تهدئة تمنع عاصفة طلبات.
- بعد نجاح التحقق الخادمي، يعاد حل سياق الصلاحية وتنفذ Delta من cursor المحفوظ، ثم تتحدث caches/الكيانات المتأثرة فقط.
- إذا تبدلت هوية المستخدم أو رفض الخادم الجلسة صراحةً، تُلغى الطلبات القديمة وتُمنع عمليات الكتابة المحلية التي تعود للسياق السابق.

### تمييز الإغلاق عن الخروج

- إغلاق تبويب/متصفح أو إعادة تحميل الصفحة ليس حدث تسجيل خروج: لا تمسح الجلسة التي يديرها Supabase SDK، ولا الـOutbox، ولا الـcursors أو snapshots.
- تسجيل الخروج الصريح يمسح جلسة Supabase المحلية، والرخصة المحلية، وملخص المصادقة، وكاش الاستعلامات الحساسة للمستخدم، وحالة الذاكرة/QueryClient، ويحرر قفل الجهاز خادميًا ضمن مهلة محددة.
- إذا كان هناك Outbox معلّق، فالسلوك الافتراضي الآمن هو إبقاؤه معزولًا ومقفلًا إلى المستخدم الأصلي حتى تتم مزامنته أو تصديره/التخلص منه بتأكيد صريح. لا يُعرض للمستخدم التالي. لا يحذف Logout المسودات بصمت؛ ذلك وحده هو ما يحقق Zero Data Loss.
- يظل logout محليًا ناجحًا حتى لو تأخر تحرير قفل الجهاز بسبب الشبكة؛ تُسجل حالة تحرير القفل كعملية استرداد قابلة لإعادة المحاولة ولا تؤخر إزالة التوكن المحلي.

## 5. التهيئة الأولى: `bootstrapDeviceContext`

تكون عملية منسقة مرة واحدة **لكل** مركب هوية:
`userId + tenantId + siteId + deviceId + localSchemaVersion + bootstrapVersion`.
لا تكتفِ بعلامة Boolean عامة مشتركة بين الحسابات أو الفروع.

### تسلسل bootstrap المقترح

1. **Prerequisites:** الجلسة online نجحت و`auth.me` أعاد user معروفًا؛ معرّف الجهاز UUID ثابت؛ حل الخادم المستأجر/الموقع وقدرة المستخدم على الوصول إليهما. لا تنفيذ لهذا التسلسل لأول مرة إذا كان offline؛ يعمل offline فقط ما سبق تهيئته.
2. **Acquire/recover local record:** أنشئ سجل `bootstrapState` scoped مع `bootstrapVersion` و`schemaVersion` و`requestId` وtimestamps وحالة كل خطوة. إذا بدأ bootstrap سابقًا ثم توقف، استأنف الخطوات الناقصة بدل التكرار.
3. **Tenant/site metadata:** احصل على بيانات السياق عبر الاستعلامات والصلاحيات الحالية؛ لا تنسخ memberships أو الأدوار إلى مصدر صلاحية محلي. خزّن أقل metadata لازمة للعرض السريع مع `lastValidatedAt`.
4. **Device/range provisioning:** احصل على `deviceId` الدائم ثم استعمل `powerhub.offlineNumbering.reserve` الموجود لحجز grants اللازمة للمستخدم المخول (مثل نطاق المشتركين العام ونطاق فواتير السنة المناسبة). استخدم request ID ثابتًا لاستئناف نفس الطلب، وتحترم الحصة والدور وقفل الجهاز؛ لا يفشل فتح مساحة العمل بالكامل إذا كان الحجز غير مطلوب أو ممنوعًا لدور المستخدم.
5. **Initial snapshot/cursors:** للكيانات التي يدعمها محرك Delta، احصل على baseline/cursor ثابت وادمج الصفحة الأولى بحدود صفحات واضحة. لا تعتمد cursor نهائيًا قبل حفظ كل عناصر الصفحة الملتزمة. للكيانات التي لم تدخل Delta بعد، استخدم استعلامها الحالي المصرح به كحل مؤقت ومعلن، دون بناء محرك تنزيل جديد؛ تتم إضافتها لاحقًا لخطة تغطية Delta.
6. **Commit local readiness:** سجل نتيجة كل خطوة بعد نجاحها. تكون علامة `isBootstrapped=true` فقط بعد حفظ السياق اللازم والـbaseline/cursors والـgrants المطلوبة بحسب الدور/المجال، أو قرار موثق بأن خطوة اختيارية غير لازمة. تحفظ العلامة داخل النطاق الصحيح، لا في global LocalStorage.
7. **Steady-state:** بعد نجاح bootstrap الأول، تتوقف عملية bootstrap عن سحب البيانات في كل تشغيل. تُدار كل تغييرات البيانات التالية عبر Outbox/Delta Sync القائم؛ يستأنف التطبيق من cursor ويحصل على الفروق فقط.
8. **Failure/recovery:** لا تُكتب علامة اكتمال عند partial failure. لا يعاد إنشاء grants أو سجلات الكيانات بلا idempotency. تعرض الواجهة الخطوة القابلة لإعادة المحاولة، مع إبقاء snapshots السابقة سليمة.

### invariants

- `bootstrapDeviceContext` idempotent: تشغيله مرتين بالـscope والـrequest IDs نفسيهما لا يخلق نطاق أرقام ثانٍ ولا يكرر كيانًا.
- `isBootstrapped` محلي ومقيّد بالنطاق وإصدار المخطط/التهيئة.
- تغيير user/tenant/site/device أو bootstrap/schema version لا يثق بالعلامة القديمة؛ يتحقق من السياق ويستأنف migration/bootstrap المناسب.
- لا يكتب bootstrap مباشرة إلى عدة caches منفصلة كأنها مصادر حقيقة؛ writes التشغيلية تمر عبر IndexedDB الموحد والـAPIs المعتمدة، ويحدّث TanStack Query من نتيجة محفوظة/معروفة.
- bootstrap ليس شرطًا لحذف/إعادة إنشاء بيانات موجودة، ولا يجري full refresh في كل login.

## 6. قاعدة الترحيل المحلي غير التدميرية

قبل بناء أي ترحيل، أنشئ inventory فعليًا لمخازن IndexedDB والأسماء والإصدارات والمفاتيح والفهارس ومصادر كتابة البيانات. لا تفترض أن كل جهاز يحمل نفس المخطط.

### المخازن المعروفة حاليًا

- `powerhub-offline-workspace` — الإصدار 4، قاعدة العمليات/numbers/Delta/field readings الحالية.
- `powerhub-offline-cache` — الإصدار 2، كاش TanStack Query وملخصات المستخدم.
- `powerhub-offline-auth` — الإصدار 1، رخصة Offline ومفتاح HMAC ومعرّف الجهاز.
- بالإضافة إلى أي مخازن legacy/field-reading ظهرت في إصدارات سابقة؛ يحدد الاسم/الإصدار من الكود الفعلي والاختبارات قبل اختيار التحويل.

### بروتوكول safe migration

1. **Inventory/checkpoint:** احفظ `sourceDatabase`, `sourceVersion`, `targetVersion`, migration ID، counts، ومفاتيح السجلات قبل البدء.
2. **Copy then validate:** انسخ إلى target مع الحفاظ على PK/UUID و`clientOperationId` و`dependsOn` وuser/tenant/site/device وpayload والحالة ومحاولات retry وnextAttemptAt/cursor/tombstone. لا تمسح المصدر في نفس الخطوة التي تنسخ فيها البيانات.
3. **Idempotency:** نفس migration ID لا يكرر عناصر target. إذا وجد المفتاح نفسه ومحتوى مختلف، لا تكتب فوقه عميانيًا؛ ضع تعارضًا في quarantine مع السبب.
4. **Validate:** قارن عدد السجلات ومجموع المفاتيح ووجود العمليات المعلقة وسلامة روابط الاعتماديات؛ اختبر عينة payload/checksum حيث ينطبق. عطل migration إذا ظهر نقص غير مفسر.
5. **Quarantine not discard:** السجلات القديمة غير محددة النطاق أو غير القابلة للتحليل تُحفظ في quarantine قابلة للتشخيص/التصدير، ولا تُعرض لغير مالكها ولا تُحذف تلقائيًا.
6. **Cutover:** حوّل القراءات/الكتابات إلى target بعد نجاح validation فقط. يظل المصدر محفوظًا لإصدار/فترة رجوع معروفة، ولا يمحى إلا بسياسة تنظيف منفصلة، بعد التأكد من عدم وجود عمليات معلقة وأن الاسترجاع متاح.
7. **Interrupted browser close:** إذا أغلق المستخدم المتصفح أثناء الترحيل، تستأنف الخطوة التالية من checkpoint. لا يعتمد النجاح على بقاء tab مفتوحًا ولا تُعتبر عمليات الذاكرة وحدها دليلًا على الحفظ.
8. **Schema upgrade:** إذا كان target version أحدث، تعالج الترقية ضمن `onupgradeneeded`/المعاملة الملائمة مع فحص التوافق. لا تفتح عدة مكونات النسخة نفسها بمنطق إنشاء متعارض للمخازن.

## 7. Delta Sync وTanStack Query: من المسؤول عن ماذا؟

- **Outbox:** يستقبل أي عملية Offline مسموح بها مرة واحدة بمعرّف `clientOperationId` ثابت. لا تتغير الهوية عند retry.
- **Server mutation:** يطبق authorization + idempotency + قواعد المجال + audit، ويعيد النتيجة النهائية. العمليات المالية/اعتمادات القراءات الحساسة لا تصبح نهائية لمجرد أن لها نسخة محلية.
- **Delta:** يبقى صاحب المزامنة اللاحقة والتغييرات الخارجية، مع cursor ثابت scoped للـuser/tenant/site/entity ومعالجة tombstones.
- **Local database:** مخزن تشغيل مستدام، مع تحديث cursor والكيانات/التغييرات في معاملات متسقة قدر الإمكان. لا تكتب cursor بعد العناصر التي يمثلها قبل التأكد من حفظها.
- **TanStack Query:** طبقة وصول/عرض وتنسيق freshness/invalidation؛ لا تكون مصدرًا ثانيًا للعمليات. بعد mutation أو Delta، تحدث الاستعلامات المتأثرة من النتيجة المحلية/الخادمية وتجنب invalidating كل QueryClient.
- **Bootstrap:** ينشئ baseline فقط ثم ينتهي؛ لا يعيد تنزيل full snapshot في التشغيل التالي إلا لأول مزامنة، أو فقد cursor/schema corruption، أو طلب full reconcile موثق.
- **نطاق التغطية:** لا يعلن المجال مدعومًا بالكامل إلا بعد اختبارات له. المجالات المالية، الموارد البشرية، الصلاحيات، الأرصدة، والإعدادات الحساسة قد تظل live-only أو read-only Offline بحسب policy لكل procedure.

| AUTH-03 | فتح tab ثانٍ مع انتهاء Access Token | لا عاصفة refresh ولا revoke نتيجة race؛ لا token فارغ يمر للطلبات المحمية |
| AUTH-04 | انتهاء المهلة/خطأ Auth مؤقت | شاشة تعافٍ واضحة، لا redirect loop ولا clear cache للخطأ العابر |
| CTX-01 | user لديه فروع/tenant متعدد | لا يبدأ تحميل البيانات حتى يحل النطاق؛ لا يخلط بيانات أي نطاق آخر |
| OFF-01 | فتح المتصفح وهو offline والرخصة/الكاش صالحان | يعرض snapshot بعد قراءة محلية؛ صفر طلبات شبكة أثناء الإقلاع في هذا المسار |

| OFF-03 | الرخصة منتهية أو مفتاح HMAC مفقود | لا استعادة غير مصرّح بها؛ رسالة دخول/اتصال مناسبة |
| BOOT-01 | جهاز جديد online | سياق صحيح، grants المطلوبة فقط، baseline/cursors محفوظة، ثم isBootstrapped |
| BOOT-02 | تشغيل bootstrap مرتين أو بعد انقطاع | لا grants أو كيانات مكررة؛ يستأنف من checkpoint |
| MIG-01 | ترحيل مخزن قديم به outbox معلق | كل IDs وclientOperationIds والاعتماديات تبقى أو تُحجر مع سبب، ولا حذف صامت |
| MIG-02 | إعادة migration | idempotent؛ لا تضاعف عدد العمليات ولا تفقد سجلًا |
| DELTA-01 | دخول لاحق بلا تغييرات | Delta صغيرة/فارغة؛ لا full snapshot بلا سبب موثق |
| DELTA-02 | تعديل/حذف من مستخدم آخر | Delta/tombstone تعكس التغيير وتحدّث local store/query cache |
| LOGOUT-01 | Logout صريح | session/lease/cache الحساس يزول فورًا؛ تحرير قفل الجهاز bounded |
| LOGOUT-02 | Logout مع Outbox معلّق | Outbox لا يُحذف ولا يظهر لحساب آخر؛ يعرض خيار استعادة/تصدير/حذف صريح |
| CLOSE-01 | إغلاق التبويب فقط | لا signOut أو revoke أو حذف طابور |
| DATA-01 | retry لنفس العملية | نفس clientOperationId والأثر مرة واحدة |

## 10. تقسيم PRs المقترح

ترقيم PRs التالي مجرد ترتيب عمل مقترح؛ لا يُنشأ أي فرع تنفيذ قبل اجتياز بوابة المرحلة السابقة.

1. **PR-A — Auth state machine/context contract:** حالة readiness واحدة واختبارات transition/tRPC gating.
2. **PR-B — Offline boot fast-path:** local-first startup وحظر الشبكة في offline startup، مع E2E للـredirect race.
3. **PR-C — Idempotent bootstrapDeviceContext:** schema/checkpoint/grants/baseline/cursors، دون محرك sync جديد.
4. **PR-D — Local migration harness:** inventory + copy/validate/cutover + quarantine + failure injection.
5. **PR-E — Query/local Delta integration:** مجال واحد في كل مرة مع قياس payloads وtombstones.
6. **PR-F — Logout/outbox lifecycle audit:** close vs explicit logout، مسح auth/cache الحساس، حفظ/استرجاع الأعمال المعلقة بأمان.
7. **PR-G — Production E2E and performance gate:** اختبار أصلي على alias الإنتاج، إثباتات CI وdeployment/log review.

يمكن دمج PRs صغيرة إذا كانت حدود الملكية واضحة، لكن لا يدمج تغيير جلسة، ترحيل بيانات محلية، وتغيير Delta cursor في دفعة واحدة دون اختبارات مستقلة.

## 11. تعريف «صفر فقدان» ومخاطر لا يمكن إخفاؤها

- لا يمكن ضمان عدم فقدان *أي تعديل لم يُحفظ أصلًا في IndexedDB* عند انطفاء الجهاز/فشل القرص؛ لذلك يجب إظهار «تم الحفظ محليًا» فقط بعد اكتمال معاملة التخزين، لا بعد تحديث React state.
- لا يمكن التحقق من إبطال جلسة خادمية أثناء انقطاع الإنترنت. Offline access محدود زمنيًا ورخصة محلية وبيانات سبق تنزيلها؛ صلاحيات online تعاد مراجعتها عند الاتصال.
- مسح كل IndexedDB عند logout، مع وجود Outbox معلق، يتعارض منطقيًا مع Zero Data Loss. الاختيار الآمن: إخفاء/قفل بيانات المستخدم ومسح الجلسة والـcaches الحساسة، مع حفظ outbox مقيّد بالمالك حتى التسوية أو حذف مؤكد.
- كتابة الرموز يدويًا في LocalStorage لا تحسن الأمان؛ XSS يمكنه الوصول إليها. نستخدم استمرار SDK، ولا نخزن refresh token في مفتاح ثاني.
- “0ms” حرفيًا لا يتحقق مع قراءة IndexedDB غير المتزامنة؛ معيارنا عدم انتظار round-trip شبكي لعرض بيانات موجودة وقياس زمن القراءة الفعلي.
- نجاح Unit/CI لا يثبت المتصفح الحي، ونجاح deploy لا يثبت الدخول بعد restart/offline. بوابة E2E المطلوبة مستقلة.

## متابعة — إصلاح كاش صفحة دليل المشتركين وإعادة التحديث عند الاتصال (2026-10-27)

- **سبب اختفاء قائمة المشتركين عند إعادة التحميل:** الصفحة لا تستخدم `powerhub.subscribers.list` فقط؛ بل تستعلم عن `powerhub.subscribers.directoryPage` مع `siteId/page/pageSize/search/subscriptionType`. كانت سياسة `isOfflineCacheableQueryKey` ترفض `directoryPage` بالكامل، لذا لم تكن نتائج الشاشة تُكتب إلى IndexedDB ولا يمكن استعادتها عند reload أو Offline.
- **الإصلاح في الكود:** توسعت سياسة الكاش لتسمح فقط بصفحات دليل المشتركين غير المفلترة، مع موقع صالح (`siteId > 0`)، حجم ثابت 20 سجلًا، ورقم صفحة بين 1 و200. تُرفض عمليات البحث النصي والفلترة بالنوع وحجم الصفحة المختلف والحقول الإضافية. تبقى السجلات محصورة بمفتاح المستخدم الحالي، وبحدود الكاش الحالية (200 سجل/مستخدم و2 MiB للسجل).
- **التحديث عند عودة الاتصال:** استعلام دليل المشتركين يحتفظ ببياناته في الذاكرة لمدة ساعة ويظل في Query Cache ساعتين؛ أضيف `refetchOnReconnect: "always"` ليعرض اللقطة أولًا ثم يحدّث القائمة في الخلفية عند استعادة الاتصال، دون منع refresh يدوي أو invalidation بعد الإنشاء/التعديل. لم تُضف هذه القائمة إلى `DeltaSyncRuntime` لأن الجسر الحالي يعالج نمط `subscribers.list` وليس نتائج directory pagination؛ لذلك يجب عدم وصف هذا الإصلاح بأنه مزامنة Delta كاملة للدليل.
- **الاختبارات المضافة:** اختبار سياسة الكاش يقبل مفتاحي tRPC المدعومين للصفحة القياسية ويرفض البحث والفلاتر والحجم غير المسموح ورقم الصفحة/الموقع غير الصالح والحقول الإضافية؛ واختبار عقد يثبت تحديث القائمة عند reconnect. لم يجرِ أي تغيير بقاعدة البيانات أو RLS أو الصلاحيات.
- **اختبار القبول الذي ما زال مطلوبًا بعد نشر الرأس النهائي:** (1) افتح `/subscribers` Online وانتظر تحميل الدليل؛ (2) أعد تحميل الصفحة Online وتأكد أن القائمة تظهر فورًا ثم تتحدث إذا كانت النسخة قديمة؛ (3) فعّل Network → Offline وأعد التحميل وتأكد من ظهور النسخة المحلية مع تنبيه انقطاع الاتصال؛ (4) أعد Online وتأكد من تحديث الخلفية. يجب تسجيل نتيجة كل خطوة لأن CI وحده لا يثبت IndexedDB في متصفح المستخدم.
- **CI السابق قبل تغييري التحديث الأخير:** على الرأس `ffa48570ee4b4556f524a9967dae6801018b4369` نجحت Security وSupabase Admin Guard وReading Cycle PostgreSQL Integration، بينما ظل PowerHub CI قيد التنفيذ لحظة تعديل `refetchOnReconnect`. لا تُنقل هذه النتائج إلى الرأس النهائي التالي؛ ستُراجع جميع البوابات مجددًا على SHA ما بعد هذا السجل.
- **الحالة:** تعديل الكاش وصفحة الدليل واختباراته مكتوب في فرع `feat/auth-local-first-single-pr`. لا يُدمج PR #359 حتى تنجح جميع بوابات الرأس النهائي واجتياز اختبار Offline اليدوي/الآلي. لا ترحيلات ولا تغييرات إنتاجية ضمن الإصلاح.
