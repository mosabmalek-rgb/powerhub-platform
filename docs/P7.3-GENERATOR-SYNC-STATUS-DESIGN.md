# P7.3 Generator Sync Status — Implementation Note

## Objective
Expose the existing Offline Work Queue state on the Generator directory without introducing a second synchronization path.

## Design constraints
- Reuse `OfflineWorkSyncPanel` and the existing `offline-work-queue` / `offline-sync-executor` path.
- Keep `clientOperationId` unchanged.
- Preserve tenant/site scoping from the existing queue and RPC contracts.
- Retry must continue through the existing executor.
- Conflict and rejected operations remain terminal according to the existing executor classification.
- Do not alter production or merge PR #21 as part of this follow-up.

## UI integration point
`client/src/pages/NetworkDirectoryPage.tsx` already imports `OfflineWorkSyncPanel` and renders it for `kind === "subscribers"`. The Generator page should render the same panel for `kind === "generators"`, using the current `siteId` and authenticated `user.id`.

The preferred change is deliberately small: move the existing panel render outside the subscriber-only block (or add an equivalent generator-only render adjacent to it) rather than implementing new queue state, retry logic, or transport calls.

## Acceptance criteria
1. Generator directory visibly exposes pending/applied/failed/conflict queue state.
2. Retry uses the existing executor.
3. No duplicate sync implementation is introduced.
4. Existing subscriber/invoice/payment paths remain unchanged.
5. Generator queue items retain UUID `clientOperationId` and current site/user scope.
6. Offline create/update, reconnect, replay, and stale-conflict behavior remain green.
