# مراجعة تكامل تطبيق app-power- مع PowerHub

**المستودع المراجع:** `mosabmalek-rgb/app-power-`  
**الوصف في GitHub:** برنامج أندرويد لقراءة العدادات  
**الفرع المراجع:** `main`  
**آخر التزام تمت مراجعته:** `0416a9e` بتاريخ 22 أغسطس 2026  
**نوع المشروع:** Android Kotlin + Jetpack Compose + Room + Retrofit

## النتيجة التنفيذية

التطبيق الحالي يمثل **نموذجاً ميدانياً محلياً جيداً للواجهة وتسجيل القراءات**، لكنه ليس متكاملاً فعلياً مع PowerHub بعد. أكبر مانع هو أن طبقة Retrofit المعرفة في `FieldReadingApi.kt` لا تُستخدم من `FieldReadingRepository`، وأن تسجيل الدخول وسحب المشتركين والمزامنة تعتمد حالياً على منطق تجريبي وتأخيرات محلية وتغيير حالة السجلات إلى `synced` دون إرسالها إلى الخادم.

بالتالي، لا ينبغي إصدار التطبيق للمستخدمين أو اعتباره متصلاً بالمنصة قبل تنفيذ عقد API حقيقية، وربط المصادقة والصلاحيات بالمستأجر والفرع، واستبدال البيانات التجريبية بالمزامنة الفعلية مع idempotency ومعالجة أخطاء قابلة للاسترداد.

## عدم تطابق عقد الاتصال

تطبيق PowerHub الحالي يعرّف واجهته التشغيلية عبر tRPC على المسار `/api/trpc`، وتُحرس الإجراءات بالمصادقة والتحقق من `siteId` وسياق المستأجر. في المقابل، تطبيق Android يتوقع REST endpoints مستقلة:

```text
POST api/auth/login
GET  api/auth/me
GET  api/field/subscribers
POST api/field/readings/bulk
POST api/field/upload
POST api/auth/refresh
```

هذه المسارات ليست عقداً مطابقة لما هو موجود في PowerHub حالياً. لذلك يجب اختيار أحد مسارين واضحين قبل البرمجة:

1. **إضافة REST Adapter رسمي في PowerHub** يحول طلبات Android إلى إجراءات خادمية مشتركة مع tRPC، مع نفس حراسة المستأجر والفرع وسجل التدقيق.
2. **إنشاء عميل Android يتكامل مع tRPC** وفق صيغة RPC الصحيحة، وهو خيار أقل ملاءمة للموبايل من REST versioned API، لكنه يتجنب تكرار عقد الخادم.

التوصية العملية هي المسار الأول: REST API مخصص للتطبيق الميداني بإصدار واضح مثل `/api/mobile/v1`، بينما تبقى إجراءات لوحة الويب عبر tRPC.

## الفجوات الحرجة قبل التشغيل

| الأولوية | الفجوة | أثرها | المطلوب |
|---|---|---|---|
| حرجة | عدم وجود مصادقة حقيقية | أي مستخدم يمكنه الدخول ببيانات وهمية، ولا توجد هوية خادمية موثوقة. | تسجيل دخول حقيقي، access/refresh token آمنان، تخزين Android Keystore، انتهاء وصلاحية وإبطال الجلسة. |
| حرجة | عدم وجود اتصال فعلي | القراءات لا تصل إلى PowerHub رغم ظهور نجاح المزامنة. | تنفيذ عميل HTTP فعلي وربطه بالمستودع، مع حالات HTTP والأخطاء والمهل وإعادة المحاولة. |
| حرجة | غياب tenant/site context | قد تُرسل قراءة إلى سياق خاطئ أو لا يمكن عزلها. | تضمين `tenantId` و`siteId` الممنوحين من الخادم وعدم الثقة بأي قيمة يحددها المستخدم محلياً. |
| حرجة | عدم تطابق نموذج البيانات | الحقول الحالية String IDs و`readingDate` النصي لا تطابق بالضرورة معرفات PowerHub الرقمية وتواريخ UTC. | عقد DTO versioned موثق، معرفات PowerHub الفعلية، UTC milliseconds أو ISO UTC، وmapping صريح. |
| حرجة | مزامنة غير idempotent | إعادة المحاولة قد تنشئ قراءة أو دفعة مكررة. | `clientOperationId` UUID لكل عملية، unique constraint خادمي، ونتيجة per-item في bulk sync. |
| عالية | رفع الصور غير موصول | `photoPath` المحلي لا يصبح `imageData` أو رابط تخزين في PowerHub. | رفع multipart أو presigned upload، checksum، ضغط قبل الرفع، وتسجيل URL/مفتاح S3 بعد النجاح. |
| عالية | تحديث المشتركين تجريبي | بيانات التطبيق قديمة أو وهمية. | endpoint حقيقي مع pagination وbranch filter وlast-sync cursor أو ETag. |
| عالية | المدفوعات ناقصة | عقد Android لا يضم طريقة التحويل ورقم الحساب المحول والمستقبل وصورة الإيصال، كما تتطلب المنصة. | توحيد Payment DTO، رفع إيصال اختياري، وإخضاع الدفع للفترة المقفلة والصلاحية. |
| عالية | التقاط الكاميرا محاكاة | قد يُحفظ اسم ملف غير موجود بدلاً من صورة فعلية. | CameraX أو Activity Result Camera، URI آمن عبر FileProvider، وإذن وقت التشغيل. |
| عالية | عدم وجود Background Sync | المستخدم قد يغلق التطبيق قبل الترحيل أو لا يعرف حالة الفشل. | WorkManager بقيود اتصال، backoff، إشعار حالة، وقائمة فشل قابلة للإعادة. |
| متوسطة | تضحية بسلامة البيانات | `fallbackToDestructiveMigration()` قد يحذف بيانات محلية عند تغيير المخطط. | migrations صريحة، اختبار ترحيل، ونسخة احتياطية/سياسة تنظيف مدروسة. |
| متوسطة | صلاحيات الموقع | وجود الصلاحية في Manifest لا يكفي للحصول على إذن وقت التشغيل أو التحقق من الموقع. | طلب runtime permission، قراءة Location، accuracy، timestamp، وسياسة رفض واضحة. |
| متوسطة | لا توجد اختبارات تكامل حقيقية | الاختبار الحالي لا يثبت الاتصال أو عزل البيانات. | MockWebServer/contract tests، اختبارات Room migration، وواجهة مزامنة offline/online. |
| متوسطة | CI للموبايل غير جاهز | لا يوجد wrapper واضح للبناء الموحد. | إضافة Gradle Wrapper، workflow Android، lint، unit tests، assembleDebug، وقيود الأسرار. |

## تغييرات مطلوبة في عقد القراءة

يجب أن يرسل التطبيق القراءة إلى PowerHub بمخطط مشابه للآتي بعد اعتماد REST Adapter:

```json
{
  "clientOperationId": "uuid",
  "siteId": 123,
  "subscriberId": 456,
  "meterId": 789,
  "readingValue": "1250.500",
  "readingAt": "2026-08-22T14:30:00.000Z",
  "captureMethod": "photo",
  "isMeterReplacement": false,
  "fieldVerified": true,
  "latitude": 31.90,
  "longitude": 35.20,
  "notes": "قراءة ميدانية"
}
```

الرقم النهائي للقراءة يجب أن يُتحقق منه في الخادم مقابل القراءة السابقة، وحالة العداد، والفترة المقفلة، والفرع، والمستخدم. لا يكفي التحقق المحلي لأن البيانات قد تتغير من لوحة الويب أو من جهاز ميداني آخر.

## خطة التنفيذ المقترحة

### المرحلة الأولى: تثبيت العقد

اعتمد فريق PowerHub عقد REST مخصصاً للتطبيق، مع توثيق OpenAPI، وأضف endpoint لتسجيل الدخول، وendpoint للمستخدم الحالي، وendpoint للمشتركين المسموحين للمستخدم، وendpoint للقراءات الفردية أو المجمعة، وendpoint رفع المرفقات. يجب أن تعيد المزامنة نتيجة مستقلة لكل عنصر حتى لا تُعتبر العناصر الفاشلة ناجحة.

### المرحلة الثانية: ربط التطبيق

أنشئ Retrofit client وOkHttp Interceptor للتوكن، وAuthenticator لتجديد access token، وRepository حقيقياً يستدعي API. احتفظ بالعملية في Room بحالة `pending`، ثم `syncing`، ثم `synced` أو `failed` مع `retryCount` و`lastError` و`serverId` و`clientOperationId`.

### المرحلة الثالثة: الميدان والصور

استبدل محاكاة الكاميرا بـ CameraX أو تدفق التقاط موثوق، وأضف ضغطاً آمناً مع الاحتفاظ بوضوح الأرقام. اربط الصورة بالقراءة بعد نجاح الرفع، وامنع حذف الصورة المحلية قبل تأكيد الخادم. طبّق صلاحيات الموقع وقت التشغيل وسجّل وقت الالتقاط ودقة الموقع عند موافقة المستخدم.

### المرحلة الرابعة: الاعتمادية والاختبار

أضف WorkManager للمزامنة عند توفر الإنترنت، وعمليات backoff، وقفل يمنع تشغيل مزامنتين لنفس الحساب، واختبارات انقطاع الشبكة وتكرار الطلب والرد الجزئي وتعارض القراءة. اختبر جهازاً واحداً ثم أجهزة متعددة على الفرع نفسه، ثم تحقق من عزل فرعين ومستأجرين مختلفين.

### المرحلة الخامسة: الإصدار

أضف Gradle Wrapper وGitHub Actions للموبايل، وأنشئ build variants للتطوير والإنتاج، وأدر عنوان API ومفاتيح التوقيع عبر أسرار CI. قبل الإصدار، نفّذ اختبار قبول ميداني يتضمن تسجيل الدخول، تنزيل المشتركين، قراءة دون اتصال، قراءة بصورة وموقع، مزامنة بعد عودة الاتصال، إعادة محاولة فاشلة، ومنع مستخدم من رؤية فرع غير مصرح له.

## قرار الجاهزية

**الحالة الحالية: غير جاهز للتكامل الإنتاجي.** التطبيق جاهز كواجهة وتجربة محلية أولية، لكنه يحتاج ربطاً خادمياً حقيقياً قبل أن يُستخدم لتعبئة قراءات يعتمد عليها النظام المالي. لا يُنصح بتعديل البيانات المحلية إلى `synced` إلا بعد وصول تأكيد من PowerHub يحمل معرف العملية وحالتها.
