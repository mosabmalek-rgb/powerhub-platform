# PowerHub — منصة إدارة مولدات الكهرباء

PowerHub منصة SaaS عربية بواجهة **RTL** لإدارة أعمال بيع الكهرباء عبر المولدات، وتشمل المشتركين والقراءات والفوترة والتحصيل والمصروفات وحسابات الشركة والفروع والموارد البشرية والرواتب وتقارير الإدارة. يعتمد النظام على عزل المستأجر والفرع، وتُسجّل العمليات المالية مع قابلية المراجعة وسجل التدقيق.

> هذه الوثيقة موجهة للمطورين ومديري التشغيل. لا تضع مفاتيح الربط أو كلمات المرور داخل المستودع؛ تُدار القيم السرية من بيئة التشغيل أو من إعدادات المشروع الآمنة.

## المزايا الرئيسية

| المجال | ما يقدمه النظام |
|---|---|
| التشغيل | إدارة المشتركين، الفروع، المولدات، التعرفات، العدادات والقراءات وإصدار الفواتير. |
| المالية | التحصيل الجزئي والكامل، طرق الدفع، المصروفات، حسابات الشركة، التسويات والفترات المقفلة. |
| التقارير | تقارير تشغيلية ومالية قابلة للتصفية والتصدير إلى CSV وExcel وPDF، مع دعم الشعار في التقارير الرسمية. |
| الموارد البشرية | الموظفون والعقود والسلف والخصومات وكشوف الرواتب ودليل الحضور والساعات الإضافية والغياب. |
| الصلاحيات | أدوار مالك المولد والمدير والمحاسب والمحصل والفني والمشاهد، مع صلاحيات مخصصة وعزل حسب المستأجر والفرع. |
| الإشعارات | طوابير SMS وWhatsApp المحلية، سجل الإرسال وإعادة المحاولة وتنبيهات حصة الرسائل. الربط الخارجي مؤجل حتى تفعيل مزود الخدمة. |
| الإدارة | مركز إدارة المنصة، خطط الاشتراك، حدود المشتركين والحسابات الفرعية والفروع، التدقيق والتنبيهات. |

## التقنية

يستخدم المشروع React 19 وVite وTailwind CSS 4 في الواجهة، وExpress 4 وtRPC 11 وDrizzle ORM في الخادم، وMySQL/TiDB للتخزين. تُستخدم Vitest للاختبارات، وExcelJS لتقارير Excel، وjsPDF وhtml2canvas لتقارير PDF، مع اعتماد التاريخ الداخلي بصيغة UTC وعرضه محلياً في الواجهة.

## المتطلبات المحلية

يلزم Node.js 22 أو أحدث، وpnpm 10.4.1، وقاعدة MySQL أو TiDB متاحة للتطبيق. يمكن التأكد من النسخ المثبتة بالأوامر التالية:

```bash
node --version
pnpm --version
```

## التثبيت

استنسخ المستودع الخاص ثم ثبّت الاعتماديات:

```bash
git clone https://github.com/mosabmalek-rgb/powerhub-platform.git
cd powerhub-platform
pnpm install --frozen-lockfile
```

لا يتم تضمين ملف متغيرات البيئة في Git. أنشئ بيئة تشغيل آمنة لدى منصة الاستضافة، أو استخدم آلية الأسرار المعتمدة في بيئة التطوير. يحتاج التطبيق عادةً إلى `DATABASE_URL` وقيم المصادقة والتخزين والتكاملات التي يوفرها قالب WebDev، ومنها:

| المتغير | الغرض |
|---|---|
| `DATABASE_URL` | اتصال قاعدة البيانات. |
| `JWT_SECRET` | توقيع جلسات المصادقة. |
| `VITE_APP_TITLE` | عنوان التطبيق الظاهر للمستخدم. |
| `VITE_APP_LOGO` | شعار التطبيق العام عند استخدامه من إعدادات المشروع. |
| `BUILT_IN_FORGE_API_URL` و`BUILT_IN_FORGE_API_KEY` | خدمات النظام المدمجة، مثل التخزين والإشعارات. |
| `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` | إعدادات Supabase عند تفعيل مصادقة أو بيانات Supabase في البيئة. |

يجب عدم نسخ قيم حقيقية إلى `README.md` أو ملفات المصدر أو سجلات CI. يستخدم GitHub Actions أسرار البيئة التي يوفرها GitHub أو إعدادات الاستضافة عند الحاجة، ولا يحتاج سير الفحص الحالي إلى أسرار لأن الاختبارات والبناء لا ينفذان عمليات قاعدة بيانات خارجية.

## تشغيل التطوير

شغّل الخادم والواجهة في وضع التطوير:

```bash
pnpm dev
```

يفتح التطبيق عادةً على المنفذ الذي تحدده بيئة WebDev. لا تفترض رقماً ثابتاً داخل كود الخادم؛ استخدم المنفذ الذي توفره البيئة أو متغير `PORT` في التشغيل المحلي.

## أوامر الجودة والاختبار

| الأمر | الوظيفة |
|---|---|
| `pnpm check` | فحص TypeScript دون إنشاء ملفات إخراج. |
| `pnpm test` | تشغيل جميع اختبارات Vitest مرة واحدة. |
| `pnpm build` | بناء الواجهة وتجميع خادم الإنتاج داخل `dist`. |
| `pnpm format` | تنسيق الملفات باستخدام Prettier. |
| `pnpm db:push` | توليد وترحيل مخطط Drizzle في بيئة مهيأة؛ استخدمه بحذر خارج بيئة التطوير. |

قبل إرسال أي تغيير، نفّذ على الأقل:

```bash
pnpm check
pnpm test
pnpm build
```

## قاعدة البيانات والترحيلات

يُعرّف المخطط في `drizzle/schema.ts`، وتوجد ملفات الترحيل داخل `drizzle/`. عند تغيير المخطط، راجع أثر التغيير على عزل المستأجر والفروع، ثم ولّد الترحيل واختبره في بيئة غير إنتاجية قبل تطبيقه. لا تنفذ أوامر حذف أو إعادة تهيئة على قاعدة الإنتاج دون نسخة احتياطية وسياسة استرجاع معتمدة.

```bash
pnpm drizzle-kit generate
```

تُدار تغييرات مخطط قاعدة البيانات في بيئة WebDev من خلال مسار الترحيل المعتمد، وليس عبر تعديل قاعدة الإنتاج يدوياً. يجب أن يحتوي كل استعلام تشغيلي على سياق المستأجر والفرع حيثما ينطبق، وأن تتحقق الإجراءات الخلفية من ملكية المعرفات قبل القراءة أو التعديل.

## بنية المشروع

```text
client/
  src/App.tsx                 مسارات التطبيق ومزودو السياق
  src/components/             مكونات الواجهة المشتركة وDashboardLayout
  src/pages/                  صفحات التشغيل والإدارة والتقارير
  src/contexts/               السياق العام، مثل المظهر
  src/lib/trpc.ts             عميل tRPC
server/
  db.ts                       مساعدات قاعدة البيانات
  powerhub.ts                 منطق PowerHub وإجراءات المجالات الأساسية
  routers.ts                  تجميع مسارات tRPC
  _core/                      البنية الأساسية للمصادقة والخادم والتخزين
shared/                       الأنواع والثوابت المشتركة
 drizzle/
  schema.ts                   تعريف الجداول والعلاقات
  *.sql                       ملفات الترحيل
scripts/                      أدوات صيانة وترحيل مساعدة
.github/workflows/ci.yml      الفحص الآلي عبر GitHub Actions
```

تستخدم صفحات الواجهة إجراءات tRPC typed بدلاً من استدعاءات REST مخصصة. أعد استخدام مكونات `DashboardLayout` ومكونات shadcn/ui الموجودة قبل إنشاء مكونات بديلة.

## المصادقة والصلاحيات

تُحرس الإجراءات الخاصة عبر سياق المصادقة وإجراءات tRPC المحمية. يتحقق الخادم من الدور ومن ارتباط المستخدم بالمستأجر والفرع قبل تنفيذ العمليات. لا تعتمد الواجهة وحدها على إخفاء الأزرار؛ يجب أن تكون الحماية الأساسية في الخادم أيضاً.

تُستخدم الصلاحيات المخصصة للعمليات الحساسة، مثل الرواتب والتصحيح الاستثنائي للعمليات المقفلة. عند السماح بتعديل عملية مالية مقفلة يجب تسجيل السبب وهوية المنفذ في سجل التدقيق، وعدم تجاوز ذلك من خلال إجراء واجهي بديل.

## الفروع والعزل

يرتبط صاحب المولد بمستأجر مستقل، ويمكن للمستأجر إدارة فرع واحد أو عدة فروع وفق الخطة والصلاحيات. يجب تمرير `siteId` أو معرف الفرع المعتمد إلى إجراءات التشغيل، مع تطبيق الفلتر الموحد في صفحات المشتركين والفوترة والتحصيل والتقارير والموارد البشرية. لا يجوز قبول معرف قادم من الواجهة دون التحقق من أن المستخدم يملكه ضمن سياقه.

## التقارير والتصدير

تدعم التقارير المالية وتقارير الحضور والرواتب التصفية حسب الفرع والفترة، وتوفر صيغ Excel وPDF عند توفر البيانات. تُدرج تقارير الرواتب التفصيلية أسماء الموظفين وبنود الأساسي والمكافآت وخصم السلف والخصومات الأخرى والصافي. ويمكن أن يظهر شعار الشركة من إعدادات هوية التقارير في رأس PDF.

تُنشأ ملفات Excel في المتصفح، بينما تُنشأ ملفات PDF الرسمية من قالب RTL عند الحاجة إلى عرض عربي منسق. يجب اختبار التصدير مع بيانات فارغة وبيانات عربية وفلاتر فرع وفترة، وعدم اعتبار ظهور زر التصدير وحده دليلاً على صحة الملف النهائي.

## الإشعارات والتكاملات الخارجية

يحتفظ النظام بسجل محلي للرسائل وحالاتها وأسباب الفشل وإعادة المحاولة. إرسال SMS عبر شركة جوال وWhatsApp الخارجي لا يُعد مفعلاً لمجرد وجود القوالب في الواجهة؛ يجب إضافة بيانات الربط في بيئة الأسرار واختبار المزود وفق سياسة الإطلاق. لا تُدرج مفاتيح API في GitHub Actions أو الكود المصدري.

## GitHub Actions

يعمل الملف `.github/workflows/ci.yml` عند كل `push` إلى `main` وعند فتح أو تحديث Pull Request على `main`. ينفذ سير العمل الخطوات التالية بالترتيب:

1. تثبيت Node.js 22 وpnpm 10.4.1.
2. تثبيت الاعتماديات باستخدام `pnpm install --frozen-lockfile`.
3. تشغيل `pnpm check` لفحص TypeScript.
4. تشغيل `pnpm test` لاختبارات Vitest.
5. تشغيل `pnpm build` للتحقق من بناء الإنتاج.

يُفضّل اعتماد Pull Request ومراجعة نجاح CI قبل الدمج إلى `main`. لا يحتوي سير العمل على نشر تلقائي؛ النشر يظل قراراً منفصلاً يحتاج إلى مراجعة البيئة والأسرار وقاعدة البيانات.

## أسلوب المساهمة

أنشئ فرعاً قصير العمر لكل تغيير، واكتب وصفاً يوضح المشكلة والحل وأثره على الصلاحيات أو قاعدة البيانات. أضف اختباراً للسلوك الجديد أو عدّل الاختبارات ذات الصلة، ثم نفّذ أوامر الجودة محلياً قبل فتح Pull Request. لا تضع بيانات عملاء حقيقية أو صور إيصالات أو سجلات تشغيل حساسة داخل المستودع.

## استكشاف الأخطاء

إذا فشل التطبيق في البدء، راجع قيمة اتصال قاعدة البيانات وسجل الخادم وتوافق إصدار Node.js. إذا فشل TypeScript، ابدأ بقراءة أول خطأ في المخرجات لأن الأخطاء اللاحقة قد تكون متسلسلة. إذا فشل البناء بسبب اعتماديات، أعد تثبيت الحزم باستخدام lockfile دون تعديل عشوائي لإصداراتها. أما مشكلات المتصفح فتُراجع من Console وطلبات الشبكة مع اختبار الدور والمستأجر والفرع المستخدم.

## ملاحظات الأمان

تعامل مع كل بيانات المشتركين والهواتف والمدفوعات والرواتب باعتبارها بيانات حساسة. استخدم HTTPS في البيئات المنشورة، وفعّل SSL لقاعدة البيانات، وامنع تسريب الأسرار إلى السجلات. راجع صلاحيات الحسابات الفرعية دورياً، واحتفظ بسجل التدقيق للتعديلات المالية والاستثنائية. لا تستخدم بيانات تجريبية أو شهادات وهمية في بيئة الإنتاج.

## الترخيص والملكية

هذا المستودع خاص ومخصص لتطوير وتشغيل PowerHub لصاحب المشروع. لا تُشارك الشفرة أو بيانات البيئة أو مفاتيح التكامل مع أطراف أخرى دون تفويض صريح.
